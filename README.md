# N2Engine Electron Frontend

A quick-and-dirty implementation of an editor frontend for my game engine project [N2Engine](https://github.com/EpicNicks/N2Engine) built to ensure the client/server architecture as well as the specific protocols are well-suited for arbitrary clients.

This is not a reflection of the final design so much as a repo of the ongoing testing.

## Running against the engine

The editor launches the engine's editor host (`N2EditorHost`, from the [N2Engine](https://github.com/EpicNicks/N2Engine) repo) itself, one host per open project. Build the engine first, then:

1. Tell the editor where `N2EditorHost` is, in either of two ways:
   - on the welcome screen, press **Locate N2EditorHost...** and pick it. The path is saved in `settings.json` in the editor's user data folder (`%APPDATA%\n2enginewebfrontend` on Windows), and **Change...** picks another. A configured path wins; or
   - set `N2ENGINE_HOST` to the executable's path before starting the editor. It is used when no path is configured.

2. Install and start the editor:

   ```
   npm install
   npm start
   ```

   `npm run dev` does the same with DevTools open (or set `N2_EDITOR_DEVTOOLS=1`).

3. Open a project folder, or reopen one from **Recent Projects**. Recent projects are kept as plain paths in `recent-projects.json` in the user data folder, and the **×** removes one from the list.

**Creating a project** (engine [#90](https://github.com/EpicNicks/N2Engine/pull/90), phase E3 of #6) runs `N2EditorHost --create <folder> --name <name>`, which writes the project (`project.n2proj` and its layout) without starting the engine. **Create New Project** asks for a folder (it needn't exist) and a name (the folder's name by default). The editor never writes the project file itself, and reads the result as engine #90 specifies:

- exit code 0: stdout has one line, `N2EditorHost created projectId=<uuid> startupScene=res://scenes/Main.scene` (space-separated key=value fields after the prefix; unknown keys are ignored, in any order). The editor then opens the folder;
- exit code 2: the folder already has a `project.n2proj`, and nothing was changed. The editor offers to open it;
- exit code 1: the host's reason, on stderr, is shown.

Whether a host can create projects is asked with `N2EditorHost --help`, which prints the usage and exits without starting the engine: a host whose usage has no `--create` is older than engine #90, and **Create New Project** is disabled with a note saying so. With a host that has projects, a folder without `project.n2proj` isn't a project (the host would refuse it with exit code 1 before its engine starts). Opening one offers to make it a project where it is: `--create` adopts the folder, keeping its files, with `--project-id from-path` so its assets keep the UUIDs they had. All of this is in `src/main/host-launcher.ts` (`createProjectWithHost`, `parseCreatedLine`, `probeHostCapabilities`) and `src/main/project-session.ts`.

The **Engine** panel (bottom right) lists the engine's subsystems from `GetEngineHealth`, e.g. `Audio Running` with `Loopback 48000 Hz, 2 channels, float32 (streamed to the editor client)`. Press **Refresh** to update it.

## The editor host process

Opening a project launches

```
N2EditorHost --project <dir> --port 0 --token-env N2_EDITOR_TOKEN --exit-on-disconnect --exit-on-stdin-eof
```

(`src/main/host-launcher.ts`, `src/main/project-session.ts`):

- **The port.** With `--port 0` the OS picks a free port. The host prints `N2EditorHost ready port=<port>` on stdout once it listens. The editor reads stdout line by line, joins lines split across chunks, strips the `\r` of Windows line endings, and ignores fields it doesn't know (the engine's `docs/logging-and-editor.html`, "The ready line"). Then it connects and says Hello. If the host exits first, or isn't ready within 30 s (`readyTimeoutMs` in `settings.json` changes that), opening fails with the host's last stderr lines (or stdout, if stderr is empty), and the host is killed. stdout is read until it ends, so the host never blocks on a full pipe.
- **The token.** Each launch gets a new random token (32 bytes, hex). It is put in `N2_EDITOR_TOKEN` in the child's environment only. It is never in the editor's own environment, on a command line (which other local processes can read), in a log line, or in anything sent to the page. The host reads the variable and removes it from its own environment. An `N2_EDITOR_TOKEN` the editor itself inherited is removed at startup, so nothing inherits it.
- **Its lifetime.** `--exit-on-disconnect` makes the host exit when the editor's session ends, so a connected host can't outlive the editor, even if the editor is killed. The editor also kills the host itself when you open another project, close the project or reload the page (which goes back to the welcome screen). Quitting (`before-quit`, `window-all-closed`, SIGINT/SIGTERM, the process's `exit`) calls `ProjectSession.shutdown()`, which is final: it kills the host and any child still being spawned (a host starting, or `--create`), and nothing is spawned after it. Each operation also runs with the generation it was queued in, and closing the project (so also a reload) starts a new one: an open that was queued before, or still waiting for the old host to die, spawns nothing. **Stop host** and **Close project** kill a host that is still starting at once, without waiting for its launch, and the open waiting on it ends as cancelled, not as an error.
- **A host that ends on its own** (it crashed, or its session ended) is shown in the toolbar and the console with its exit code and last output lines. That includes a host that dies between its ready line and the editor's Hello: the failed connection waits briefly for the process's exit, and reports that instead of the closed connection. **Start host** launches a new one for the open project. **Stop host** sends `Shutdown` and kills the host if it hasn't exited after 3 s. **Restart host** stops it and launches a new one.
- **Before the first Hello.** A host started with a token ignores connections that never say Hello, so `--exit-on-disconnect` can't end a host whose launcher died between spawning it and connecting. The editor kills it on every path it can run code on. For a launcher that is killed outright, the editor keeps the host's stdin open as a pipe and never writes to it: the pipe closes when the editor dies. The editor passes `--exit-on-stdin-eof` (opt-in in the engine), so the host exits when that pipe closes.

The launcher adds `--editor-extensions` only for a project folder the user trusted (see "Editor extensions"); a host for any other project, a play host and a remote host never get it from the editor.

The toolbar shows the host's state: starting, connected, stopped, exited or failed. The page sees it through `window.host` and never picks a host, port or token.

## Remote engine

> **Not yet tested against a real server.** Remote mode has only been run against fakes in the unit tests, never against a real ssh server or a cloud host. Even the `Allocated port N for local forward` line ssh prints, which the editor waits for, is taken from OpenSSH's source, not observed. Expect rough edges, and please report what you hit.

The welcome screen has two modes: **Local engine (exe)** (everything above: the editor launches `N2EditorHost` for a project folder) and **Remote engine**, which connects to an `N2EditorHost` that is already running somewhere else, for example on a cloud machine. The connection goes through an SSH tunnel the editor opens itself, so the host stays bound to loopback and only `sshd` is exposed (frontend issue #21; a host that serves TLS itself can be reached at its own address instead, see **Remote editing: direct address (TLS)** below; engine issue [#108](https://github.com/EpicNicks/N2Engine/issues/108)).

**Setting it up, step by step.**

1. **Make up a token.** The host does not generate one: it reads whatever string is in the environment variable named by `--token-env`, and the editor sends the same string. Generate a long random one, for example in PowerShell:

   ```
   -join ((1..32) | % { '{0:x2}' -f (Get-Random -Max 256) })
   ```

   or in bash: `openssl rand -hex 32`.

2. **Start the host on the remote machine.** Pick a fixed port and put the token in the environment, not on the command line. In bash:

   ```
   N2_EDITOR_TOKEN=<token> N2EditorHost --project <dir> --port 7777 --token-env N2_EDITOR_TOKEN
   ```

   In PowerShell:

   ```
   $env:N2_EDITOR_TOKEN='<token>'; .\N2EditorHost.exe --project <dir> --port 7777 --token-env N2_EDITOR_TOKEN
   ```

   The host removes the variable from its own environment after reading it. Keep the token out of your shell history (for example, set it from a file or a secrets manager rather than typing it into a logged shell). Without `--token-env`, anyone who can reach the host controls it.

3. **Fill in the editor's Remote form** (see **Connecting** below): `user@host`, the SSH port, optionally an identity file, the host's port (`7777` above), and the same token.

Leave `--bind` at its default (loopback): the tunnel reaches it there. Don't pass `--exit-on-disconnect` or `--exit-on-stdin-eof` (they are for a host the editor launches): the host should outlive the editor's session. The host serves the project it was started with.

**Always start a remote host with `--token-env`.** Only a host with an access token ignores a connection that never says Hello. A host started without one treats any connection as a session (with `--exit-on-disconnect`, closing it would stop the host) and accepts whatever token the form sends, so the token is also what keeps a stray local connection to the tunnel's port out.

**Connecting.** Choose **Remote engine** and fill in:

| Field | |
|---|---|
| SSH address | `user@host` (an IPv6 address works without brackets) |
| SSH port | optional; ssh's default (22, or what `~/.ssh/config` says) otherwise |
| Host's editor port | the `--port` the host was started with |
| Identity file | optional, a private key file; without one ssh uses the agent, the default keys and `~/.ssh/config` |
| User | optional; the user the token was made for, for a host with a tokens file ("Users and roles" below). Not the ssh user |
| Access token | the host's `N2_EDITOR_TOKEN` (or a user's token) |

Everything but the token is remembered as **Recent Remotes** (`recent-remotes.json` in the user data folder, next to `recent-projects.json`); click one to fill the form in. The token is asked every time: it is never saved.

**SSH setup.** The editor runs the system's `ssh` (OpenSSH): on Windows `%SystemRoot%\System32\OpenSSH\ssh.exe` when it exists (Windows 10 and later ship it), else `ssh` from the `PATH`; elsewhere `ssh` from the `PATH`. It runs with `BatchMode=yes`, so it can't ask for anything: use a key without a passphrase or one loaded into an agent. The host's key must already be in `known_hosts` (host-key checking is ssh's own): connect once in a terminal with the same ssh the editor runs, `ssh -p <port> user@host`, and answer yes. Windows' OpenSSH and Git's ssh keep separate `known_hosts` files, so the one on your `PATH` may not be the editor's; when the key isn't trusted the error names the ssh the editor ran and the command to run once. Hosts defined in `~/.ssh/config` work as `user@alias` (aliases may have underscores). The editor adds `-o ControlMaster=no -o ControlPath=none` so a `ControlMaster`/`ControlPersist` setting can't hand the tunnel to a background master that would outlive it. Don't put a `LocalForward` for that host in your ssh config: it is forwarded too, and with `ExitOnForwardFailure` a port clash ends the tunnel. If connecting fails, the error shows ssh's last stderr lines (`Permission denied (publickey)`, `Host key verification failed`, `connect failed: Connection refused` for a wrong host port, and so on).

**What the editor runs.** Without a shell, with the arguments as an array (`src/main/ssh-tunnel.ts`):

```
ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes -o ControlMaster=no -o ControlPath=none -o LogLevel=INFO -o ConnectTimeout=15 -o ServerAliveInterval=15 -o ServerAliveCountMax=3 \
    -L 127.0.0.1:0:127.0.0.1:<host port> [-p <ssh port>] [-i <identity file> -o IdentitiesOnly=yes] -- user@host
```

The address, ports and identity file are validated first: an address that starts with `-` (or has characters a host name doesn't) is refused, so it can't become an ssh option, and `--` ends ssh's options before the destination. The local port is `0`: ssh picks a free one itself and prints `Allocated port <n> for local forward to ...` (at `LogLevel=INFO`, which the editor sets) once it has authenticated and listens. The editor waits (up to 25 s) for that line and only then connects to `127.0.0.1:<n>` and says Hello with the token, as in local mode. It never probes a port: a connect test would trust whatever listens there, and another local process could have taken a port picked in advance while ssh was still authenticating. After Hello it checks ssh is still running.

**The token.** It goes from the form to the main process and into `Hello`, and nowhere else: not a command line or the environment of ssh, not a log line, not the host state or an error message, and not `recent-remotes.json`. The form clears it as soon as **Connect** is pressed, so a failed attempt asks for it again.

**What is different from local mode.**

- The editor edits whatever project the host has open: there is no project picker, **Create New Project** or recent project. **Start host**, **Stop host** and **Restart host** aren't shown (the host isn't the editor's), and nothing ever sends `Shutdown` to a remote host or kills it. **Disconnect** (the toolbar's Close project) closes the tunnel, as do a page reload and quitting (`ProjectSession.shutdown()` is final here too: it kills ssh, and nothing opens after it); the host keeps running.
- If the tunnel dies (the network drops, ssh is killed, the server ends the session) the toolbar shows `The SSH tunnel ended`, with ssh's last stderr lines as the tooltip and in the console, like a host that exited. If only the host's connection ends while the tunnel stays, it reads `Disconnected from the remote host`. **Disconnect** and connect again.
- **Play mode is off.** Play launches a second `N2EditorHost` on the editor's machine, from the project's folder, which a remote engine neither has nor can give; the Play button is disabled with that explanation, and the main process refuses `window.play.start()` too.
- **Audio and the viewport** go through the same connection and the tunnel, unchanged: the audio stream (48 kHz stereo float32, about 3 Mbit/s) and the viewport's frames need that bandwidth, and the 25 ms `GetAudio` polling is timed from each response, so a link with a round trip near or above the 100 ms jitter buffer can underrun. Not measured yet (see the pull request).
- Assets, scenes, the hierarchy, the inspector, undo and the console work as before: they only ever asked the host. The editor never touches the remote project's files directly.
- **Disconnect** with an unsaved scene asks whether to save first; "Disconnect without saving" doesn't lose the changes: they stay in the remote host's memory, which autosaves when the editor disconnects.

**Known limits.** Connecting can't be cancelled while ssh is still connecting (it ends by its own timeout, 25 s at most). Ending the tunnel sends ssh a plain kill (`SIGTERM`, `TerminateProcess` on Windows) with no escalation, as local mode does for its host. Domain users (`DOMAIN\user`) and `user@host:port` aren't accepted in the address (use the SSH port field; put a domain user in your ssh config). There is no identity-file picker, and the ssh agent or key must work without a prompt. Play mode isn't available.

## Remote editing: direct address (TLS)

> **Not tested against a real cloud host.** The TLS and pinning code is unit tested against a local TLS server with a throwaway certificate, and the form has never been run against an N2EditorHost started with `--tls` on another machine. Expect rough edges.

Besides the SSH tunnel, **Remote engine** has a second tab, **Direct address (TLS)**, for a host that is reachable at an address of its own and serves TLS itself (engine PR #112; see the engine's `docs/logging-and-editor.html`, section "ready line"). Nothing else needs installing on the host machine: no sshd, no tunnel.

**Host side.** Start `N2EditorHost` with `--tls`, a fixed `--port`, a `--bind` the editor can reach and an access token (`--token-env`, as above). It serves TLS 1.2+/1.3 with a self-signed certificate, made on first use, and prints its fingerprint in the ready line:

```
N2EditorHost ready port=7777 tls=1 fingerprint=<64 lowercase hex digits>
```

**Editor side.** Fill in the host address, the port, the access token (and the optional **User**, for a host with a tokens file) and leave **TLS** on. The **Expected fingerprint** is optional:

- **With it** (copy it from the host's ready line), the editor pins the host up front: it connects only if the certificate the host presents has exactly that SHA-256 fingerprint. Colons, spaces and upper case are accepted when typing.
- **Without it**, the editor does the TLS handshake only (nothing is sent) and shows the fingerprint the host presents. Compare it with the ready line, by a channel you trust, and press **Trust this fingerprint and connect**. Nothing is ever trusted silently.

**Trust on first use.** The confirmed fingerprint is remembered per host and port, with the time it was first seen, in `pinned-fingerprints.json` in the user data folder (no secrets in it). The next connect to that host and port uses the pin without asking. If the host later presents a different certificate (its identity file was replaced, or something else answers on that address), the editor refuses to connect and the error and the form name the pinned and the new fingerprint. If the change is expected, press **Forget pin**, connect again and confirm the new fingerprint; otherwise do not connect.

**Order of events.** The TCP and TLS handshake, then the pin check, and only after it passes is `Hello` (and with it the access token) sent. A host whose certificate doesn't match gets no bytes from the editor, the token included. Node's own certificate checks are off (the certificate is self-signed and named for nothing in particular): the pin is the only check, with no extra dependency (`src/protocol/tls-pin.ts`).

**Plaintext.** The **TLS** box may be turned off only for this computer's loopback (`localhost`, `127.x.x.x`, `::1`), for a host started without `--tls`. The editor refuses a plaintext connection to any other address, in the form, the main process and the protocol client alike.

**What this does not give.** A single `--token-env` token is still one shared secret for the whole host (a tokens file gives per-user tokens and roles, see "Users and roles"); there is no rate limiting of guesses (see the engine's docs for what its token model does and doesn't give). A fingerprint pin proves the host is the one you confirmed, not that it is a good host, and it is only as good as the first confirmation (an attacker present at the first connect, when you confirm blindly, is trusted). There is no list of recent direct remotes yet (only the pins are remembered), and as with the tunnel, the editor edits whatever project the host has open and **Play mode is disabled** for a remote engine.

## The console

The **Console** tab of the bottom panel shows the host's log. The editor reads it with `PollEvents` about every 100 ms (`src/renderer/console-store.ts`, with the `EventPump` in `src/protocol/event-pump.ts`). It follows the epoch rule in the engine's docs ("Events: PollEvents and the log ring"):

- the first poll sends epoch 0 and seq 0, which gets everything the host still has, startup lines included;
- every later poll sends the last response's `epoch` and `nextSeq`, across reconnects too, so nothing is missed or repeated;
- a newly launched host (a restart, or another project) starts again from (0, 0), so its whole log is read;
- a response in an epoch other than the one asked about (another host process, or the ring starting over when its seqs ran out) starts a new log, and the console says so;
- `dropped` events (ones that fell off the host's ring before the editor read them) are noted with their count.

The console also shows the editor's own notes: a host starting, a host exiting with its last output, and rendering stopping. It keeps the last 5000 lines. **Clear** empties it; the host's log isn't read again.

**Filters** (roadmap FE7; `console-filter.ts` and `console-store.ts`, pure and tested in Node). All of them combine, and they are remembered per project (see "Preferences and keyboard shortcuts").

- **Level** boxes (Info, Warnings, Errors), each with the number of lines it has among those that pass the source and text filters (a level switched off still says how many lines it would add).
- **Source** boxes (Host, Game, Editor, Extension). The engine's log events have no category or tag today (the roadmap defers one, decision U20), and its lines have no prefix to read one from, so a source is not guessed from the text: it is the one the line was added with (the host's log, the game's, the editor's own notes). A line with a source that isn't registered counts as the host's. A feature that adds lines from elsewhere registers its source once, `consoleSources.register({ id: "extension", label: "Extension" })` (editor extensions do this: see "Editor extensions"), and gets a box.
- **Text** filter with the matches highlighted: plain text, ignoring case, by default. **Aa** matches the case and **.\*** reads the text as a regular expression (off by default). A pattern that isn't valid shows the reason under the toolbar and filters nothing (so the list doesn't flash empty while a pattern is typed); a pattern over 200 characters is refused the same way, and a regular expression is tried on the first 4096 characters of a line. The expression runs on a small linear-time matcher (`src/renderer/safe-regex.ts`, a Pike VM, no backtracking: deciding whether a line matches takes at most line length x program size steps; highlighting finds every match with one run per match, each of which can look past its own end, so after the first match a line's highlighting is capped at 64 steps per character of the line and past that keeps the matches found so far). The matching is not done by the engine's RegExp, which only checks the syntax, so `(a+)+$`, `((a+))+` or `(a|aa)+$` cannot hang the page and no heuristic guessing at bad shapes is needed. Many long lines add up even when each is linear, and the log keeps arriving, so a pattern's work draws on two buckets of steps, kept apart so that highlighting can never starve the filter: one for testing the lines (once per change of the lines or of the pattern, the one result shared by the list, the level counts and the source counts, and remembered per line, so a new batch of lines costs only its own lines) and one for highlighting the rows. The testing bucket holds 15 million steps and refills at 3 million a second, the highlighting bucket 5 million and 1 million a second: together 20 million steps is the most one update can spend (a quarter to half a second of matching on a desktop; testing a literal pattern can cover about five million characters of lines) and 4 million steps a second (5 to 10 percent of a core) the most the filter spends on average while lines stream in; a full console of short lines and ordinary patterns is far below both. When testing runs its bucket dry (for example `[a-z]{1,60}[0-9]{1,60}q`, about 740,000 steps on a 4096-character line, over 30 such lines, or lines streaming in faster than the refill), the regular expression turns off for that pattern in the list and the counts alike, "too slow on the lines in the console" shows under the toolbar, and nothing is filtered until the pattern is edited (a new pattern starts with full buckets). When highlighting runs its bucket dry, the rows past that point are shown without marks and are marked on a later render once the bucket has refilled; the filter stays on, since testing has its own bucket. The editor applies a changed text, **Aa** or **.\*** 200 ms after the last change (clearing the text applies at once), so typing a pattern compiles one matcher when typing pauses rather than one per keystroke. It was chosen over a Web Worker with a time budget because the filter is applied synchronously while the list renders (a worker would make every filter pass asynchronous), and over a library because there is nothing to pin or license. It reads the usual JavaScript syntax (literals and escapes, classes, `\d \w \s`, `^ $ \b`, groups, `|`, `* + ? {n,m}` and their lazy forms); back-references, look-ahead and look-behind, named groups, and a counted repeat that expands past 600 steps (such as `(a{50}){50}`) show "Not supported in the filter" with the reason and filter nothing, like an invalid pattern.
- **Collapse** turns identical lines (same level, source and text) that follow each other, among the lines shown, into one row with a count badge; the counts of the level boxes still count lines.
- Every view is one pass over the (at most 5000) lines, so the list renders as it did before the filters.

## The hierarchy and scenes

The **Hierarchy** panel (bottom right of the editor, `src/renderer/hierarchy-panel.tsx`) shows the loaded scene's objects as a tree, read with `GetHierarchy` (protocol 1.4). Its logic is in two framework-free modules, tested in Node: `hierarchy-tree.ts` (the tree built from the flat list, the rows shown, the selection rules, where a drag may drop) and `hierarchy-state.ts` (`HierarchyState`: the objects, what is expanded, selected and being renamed, as signals, and the actions).

- **Selection.** Click selects, Ctrl+click toggles, Shift+click selects the rows between the anchor and the click. The last one clicked is the primary selection: it is the object the inspector shows. Arrow keys move through the rows (Shift extends), Right opens an object (or goes to its first child), Left closes it (or goes to its parent).
- **Rename.** F2, double-click on the name or **Rename** in the context menu. Enter or leaving the field sets the name (`SetEntityProperties`), Escape cancels; an empty or unchanged name sends nothing.
- **Active.** The checkbox before each name sets the object's own `active` flag. An object that is inactive because an ancestor is (`activeInHierarchy`) is greyed.
- **Create.** **+ Add** (and the context menu on the empty space) creates a root, and **Create ... Child** on an object makes a child of it, as the last one (`CreateEntityEx`). The presets are Empty, Cube, Sphere, Quad, and the Directional, Point and Spot lights. The new object is selected and its name opens for renaming.
- **Duplicate** (Ctrl+D) copies each selected object with what is under it, right after the original (`DuplicateEntity`), and selects the copies. **Delete** (Del) destroys the selected objects with what is under them (`DestroyEntity`), after asking when that is more than one object. Several objects deleted, duplicated or moved together are one undo step (see "Undo, redo, edit groups and autosave").
- **Drag and drop.** Drag an object (or the selection) onto the upper or lower quarter of a row to put it before or after that row, in the middle to make it a child, or onto the empty space to make it the last root. A blue line or box shows where it will land. Dropping onto an object itself or anything under it is refused (the engine would refuse it too). A reparent keeps the object where it is in the world (`keepWorldTransform` true: its local transform changes), like Unity. The calls are `SetEntityParent` with the `siblingIndex` the object ends up at: several dragged objects are placed one after another before the first sibling that isn't moving. Dropping below an object that is open puts it before that object's first child, where the line is drawn.
- **Following the scene.** After each of its own actions the panel reads `GetHierarchy` again, because the siblings whose index shifted are only fresh there. Other changes arrive as `sceneChanged` events: the panel reads again when the store's `lastSceneChange` says the scene changed, unless the hierarchy it holds was read at or after the newest revision an event named (so the event that follows an action of its own costs no second read). A change can't be narrowed to the objects it lists, because a reparent or a delete moves the indices of siblings it doesn't list; the ids go to the inspector, which reads its object again when it is listed. A full change (another scene was loaded, events were missed) reads everything, and keeps the selection and expanded objects that still exist.

- **Search** (roadmap FE6). A search box above the tree (Ctrl+F in the list focuses it; Escape clears it, and on an empty box goes back to the list). Words match names by part, ignoring case; `t:Type` matches a component type name by part, `tag:x` a tag by part, `layer:N` the layer exactly; every word has to hold, and a half-typed token (`t:`) is ignored instead of emptying the list. The result is the tree cut down to the matches and their ancestors, all of them open (what the user had expanded is untouched and comes back when the search is cleared), or, with **List**, a flat list of the matches each with its path. The panel says how many objects match. Clicking, Shift-click and the arrow keys work on the rows shown; Right goes to the first shown child and Left to a shown parent. While a search narrows the rows **drag-and-drop reparenting is off** (the drop places it hides are not all shown, so rows are not draggable and a drop does nothing), and Delete and Duplicate act only on the selected objects that are shown. Creating an object ends the search so the new object is visible for renaming. Filtering is one O(n) pass over the objects, recomputed only when the tree or the text changes (`filterHierarchy` in `hierarchy-tree.ts`). The text and the mode are remembered per project.

**Scenes.** The toolbar has **New scene**, **Open scene** (a menu of the project's scene files), **Save scene** (Ctrl+S) and **Save as...**. The host owns scene files: the editor calls `OpenScene`, `NewScene` and `SaveSceneToFile` with `res://` paths (`res://` is the project's `assets` folder) and never writes them itself. A path typed without `res://` or `.scene` gets them; the host checks the rest and refuses a `NewScene` over a file that exists. A scene with no file asks for a path when saved. The scene's name in the toolbar has a `*` after it, and the hierarchy panel's title too, while it has unsaved changes (`revision` differs from `savedRevision`). Before open, new, restarting or stopping the host, or closing the project would discard them, a dialog offers Save, Discard or Cancel (the host is asked for the scene's revisions first, so an edit made a moment ago counts); closing or reloading the window asks too (the page vetoes with `beforeunload` and the main process shows the question). A path that is a file on disk, a folder or has no file name is refused with a message before the host is asked. An object with no transform (`GetEntityTransform` refuses it) is inspected without a Transform section. Double-clicking a `.scene` in **Assets** opens it, **Open scene** lists the scenes the host listed, and **New Scene** in a folder's menu offers a path in that folder.

## The inspector

The **Inspector** panel (`src/renderer/inspector-panel.tsx`) shows the selected object (the hierarchy's primary selection): its name, active flag, tag and layer, its local transform (see "Transform" below; "This object has no transform" for an object without one), and its components, each as a collapsible card with an enabled checkbox and a remove button. It is built on the protocol 1.5 commands (engine PR #93): `GetEntity` lists the components with their saved values, `GetComponentTypes` gives every type's schema (read once per connection), `GetLuaFields` a Lua component's script fields, and `SetComponentFields`, `AddComponent` and `RemoveComponent` change them. The logic is framework-free and tested in Node: `inspector-fields.ts` (kinds, values, checks, partial updates, the Add Component grouping), `inspector-state.ts` (`InspectorState`, the signals and actions) and `asset-lookup.ts`; `inspector-editors.tsx` is the DOM around it.

- **An editor per `FieldKind`.** Bool is a checkbox, Int and Float a number box (with a slider when the field has both `min` and `max`), String a text box, Enum a drop-down of `enumOptions`, Vector2/3/4 and Quaternion one box per axis (a quaternion is edited as its x, y, z, w, which the host normalises: no Euler angles, so no convention is guessed), Color a colour picker (+ alpha for `{r,g,b,a}`; `typeName` says the JSON is `{r,g,b,a}`, `{x,y,z}` as for Light's colour, or `{x,y,z,w}`), Json a text area that must parse, and a kind this client doesn't know is edited as JSON. Reference kinds are slots: AssetRef (a UUID, shown by file name), GameObjectRef (shown by the object's name), ComponentRef (an object and then one of its components of the field's type), and their lists (add, change, remove items). Hidden fields aren't shown; read-only ones are disabled.
- **Checks before sending.** What is typed is checked against the field (a whole number for an Int, the C++ type's limits from `typeName`, a range clamps as the host does, every axis present, an option of the enum, a UUID or empty for a reference) and refused in place with the reason; the host checks again and is the authority.
- **Edits.** A change shows at once and is sent after 250 ms without another one (a slider sends one request), merged with the edits made meanwhile, one `SetComponentFields` per component at a time. Only what differs from the stored values is sent (setting a field to what it is sends nothing), and the echo keys `uuid` and `scriptPath` are never sent. The answer (the values as stored: a clamped number, an enum's canonical spelling) replaces what was shown. The host takes a request all or nothing, so a refusal puts back every field of that request and its message is shown under the component; edits made after it are still sent. A read of the object that began before an edit was answered can't undo it. Ctrl+S sends what is pending before it saves the scene, and changing the selection sends it to the object it was made on.
- **Lua components.** A script's fields (from `GetLuaFields`, each with container `scriptData`) are edited inside `scriptData`, and a reference there is written `{"$ref": uuid}`. Changing the script (`scriptUUID`) is sent without `scriptData` (the host refuses both together; data written for the previous script is dropped, with a note), then the script's fields are read again. They are also read again when `assetsChanged` arrives, since a script may have been edited.
- **Assets.** The asset slots choose from the host's `ListAssets` (see "The assets panel"): files and a model's parts, by UUID, plus the engine's built-in meshes (Cube, Sphere, Quad). An asset dragged from the **Assets** panel onto a slot (or one picked from the slot's list, which is searchable) sets it, if its resource type is the field's `assetType`; otherwise the slot says "X is a Texture; Font expects Font". An object dragged from the hierarchy can be dropped on a GameObjectRef slot.
- **Add Component** lists the types by group (Rendering, Physics, Audio, UI, Scripting, Other: a name pattern in `inspector-fields.ts`; a game's own types are Other) with a search box; a singleton type (`AudioListener`, `Canvas`, `RectTransform`) the object already has is shown disabled. **Remove** asks first (Undo puts the component back, with the references to it). A component type that is in the scene but not registered can't be edited: it is listed as such.
- **Text effect passes.** A Json field whose `typeName` is `TextPass[]` (`effectPasses` of `TextRenderer` and `UIText`, with an engine that marks it) gets a pass list editor instead of the JSON box: a row per pass (colour, offset, width, softness, order) with remove and move buttons and an Add pass button. Each edit commits the whole array. Orders above 0 are not supported by the engine yet (it clamps them to 0); the editor shows them as they are. A value that is not a pass list is edited as JSON. The list logic is in `inspector-fields.ts` (`readPassList` and friends).
- **Following the scene.** The inspector reads the object again (`GetEntity`) when a `sceneChanged` event lists it, or is full.
- **Transform (FE5, roadmap decision U5).** The Position, Rotation and Scale rows are the object's LOCAL transform, the one the gizmo moves: `GetEntity` gives it (position, quaternion, scale) and an edit is one `SetLocalTransform` with the whole local transform, so one commit (type, then Enter or leave the box) is one undo step. The legacy world-Euler `GetEntityTransform`/`SetEntityTransform` are no longer used by the editor (the host keeps them for other clients). Rotation is shown as Euler angles in DEGREES in the engine's convention (`euler.ts`): x about X, y about Y, z about Z, applied X then Y then Z about the fixed axes (R = Rz * Ry * Rx, the engine's `Quaternion(pitch, yaw, roll)` with pitch = x, yaw = y, roll = z), read back with x and z in (-180, 180] and y in [-90, 90]; at y = +-90 (gimbal) z is 0. The quaternion is what is stored and sent: the triple last typed is kept while it still means the stored rotation (`stableEuler`: 180 doesn't turn into -180, 540 stays 540, a read doesn't drift), a move or a scale edit sends the stored quaternion untouched, and Euler angles that mean the stored rotation are shown but not sent. A change by the gizmo, a script, another client or Undo is shown as the canonical angles. A refusal puts the old values back. World values are not shown.
- **Several objects selected (multi-edit).** With two or more objects selected the panel shows "N objects" and their shared fields (`inspector-multi.ts`, `MultiInspectorState`): active, tag, layer, the local transform per axis (rotation as each object's Euler angles), and the first component of each type that every object has (a `LuaComponent` only when all run the same script). Where the objects differ the box shows a dash (a checkbox is indeterminate, a drop-down shows a dash). An edit applies to ALL of them inside ONE edit group named "Edit N objects" (one undo step), one request per object, only to the objects whose value differs; a vector edit changes only that axis and each object keeps its others. Bool, Int, Float, String, Enum, vector and Color fields are multi-edited; references, lists and JSON are edited one object at a time (the card says how many are left out), and the name is single-object only; Add Component and Remove apply to all of them (see "Inspector multi-edit (FE11)" below, which also says what happens when an object refuses an edit). Read-only (a play session, a viewer) disables every box. A slider or colour drag waits for a 250 ms pause before it is sent. Undo and Save send a drag that is still waiting first. A colour pick changes only the RGB channels (each object keeps its alpha). In this view rotation is always each object's canonical Euler angles (a typed y of 120 reads back as x 180, y 60, z 180), and angles a whole turn apart are not shown as mixed.
- **Read-only.** `InspectorState.setReadOnly(reason)` makes every editor disabled and every change refused (the rule for a play session, whose host the inspector shows but doesn't change: engine docs, "The inspector is read-only while playing"). Nothing sets it yet, since there is no play mode. Undo and redo are disabled while it is set (the host refuses them outside edit mode).
- **Undo and redo** are the next section.

## Project settings

Roadmap phase FE9 (decision U6). A closable panel, **Project Settings** (a tab beside the inspector, from the Window menu), over `GetProjectInfo`, `SetProjectSettings` and `SetStartupScene`. Left a list of sections, right a form for the selected one.

- **Sections.** General (name, id, engine version, startup scene picker over the scene list), Physics, Rendering, Math, Determinism, Layers (32 names and the collision matrix: see "Layer collision matrix"), Extensions (the host's editor extensions: see "Editor extensions"), Input (`actionMaps` as a validated JSON editor) and Raw JSON (the whole `settings` object, with a confirm before Apply). Fields come from typed tables in `project-settings-schema.ts` (label, type, range, default, help), with the engine's ranges checked before anything is sent.
- **Applying.** Edits are held per section. **Apply** sends only the changed keys as an RFC 7386 merge patch (`null` for a cleared value); the answer replaces the form. **Revert** drops the unsent edits. After an Apply, **Restore previous values** puts the old values back as a new patch: settings are not in the host's undo history, and the panel says so. A host refusal or warning is shown under the section and the edits are kept.
- **Restart badges.** `physics.gpu`, `physics.deterministic`, `physics.backend`, `math.simdTier` and `determinism.luaSeed` are read only at `Application::Init`: they carry an "applies after restart" badge and a note after Apply.
- **Roles.** The whole `determinism` block is admin-only on a host with tokens: the section is read-only with the reason for an editor or viewer, no UI path (the Raw JSON section included) sends it for a non-admin, and a `forbidden` answer from the host is shown. A viewer or a read-only host sees every section disabled. The `luaSeed` field carries the engine's warning that a constant hash seed makes hash flooding possible.
- **Adding a section** (Network from B11 is still to come; Extensions registered itself this way): one `settingsSections.register({id, title, order, component, logic?, requires?})` call (`project-settings-registry.ts` documents the contract); the panel's code does not change. With `logic.build` the panel adds Apply, Revert, the host error and the restart note under the component.
- **Not verified in a real Electron window or against a live host yet:** the look of the panel, and a round trip (apply a gravity, change a restart-only field and restart).

## Layer collision matrix

Roadmap phase FE9b. The Layers section of **Project Settings** has, under the 32 names, the collision matrix as a grid of checkboxes: a row and a column per layer, ticked where the two layers' colliders touch (contacts and triggers).

- **What is sent.** The engine's format (`Layers.cpp`, `Serialize`/`Deserialize`): `layers.collisionMatrix` is an array of exactly 32 row masks, each an integer in 0..0xFFFFFFFF, where bit `b` of row `a` (`1 << b`) means layer `a` collides with layer `b`. Apply sends all 32 rows (a merge patch replaces an array whole) as `{"layers": {"collisionMatrix": [...]}}`, plus `layers.layers` only when a name changed too; the names already saved are kept by the merge. Bit 31 is written unsigned (`>>> 0`), so every row is one the host takes.
- **Symmetric.** The host treats a pair as colliding only when both rows say so. A pair is one edit key (`pair.a.b`, lower layer first), so ticking row a, column b ticks row b, column a too, and Apply sets or clears both bits. A project matrix whose rows disagree is shown the way the engine reads it (not colliding); one that is not 32 masks is flagged and shown as every layer colliding (the engine's default), and Apply writes a valid one.
- **Unnamed layers** are left out of the grid until **Show the unnamed layers** is ticked (the built-in and named ones are always shown). Each row and column header has a checkbox that ticks (or, when all are ticked, clears) every pair of that layer that is shown; it is mixed when some are. Hidden layers are not changed by it.
- **Applying.** Dirty cells are marked, and Apply, Revert and Restore previous values are the Layers section's, with the names: a bad name holds back the whole section. The rules are the other sections': read-only for a viewer, a read-only host or a play session; an editor can change it (only determinism is admin-only).
- **Code.** The model is in `project-settings-schema.ts` (`collisionMatrixOf`, `pairKey`, `setRowsPair`, `buildLayersPatch`), the grid in `project-settings-sections.tsx` (`CollisionMatrixEditor`); `ProjectSettingsModel.setEdits` sets a row's pairs in one update. Tests: `src/test/layer-collision-matrix.test.ts` (the model) and `src/test-dom/layers-matrix.test.tsx` (the grid).
- **Not verified in a real Electron window or against a live host yet:** the look of the grid (rotated column headers) and a round trip with the engine.

## Editor extensions

Roadmap E-X4 (design `lua-editor-extensions`, decisions D1 to D12), over protocol 1.14.0 and 1.15.0. A project can have Lua **editor extensions**: .lua files in its `editor/` folder (beside `project.n2proj`, not in `assets/`) that add items to a **Tools** menu. They run on the editor host, in a sandbox of their own, never in this window: the page only receives data (names, menu paths, form fields, messages) and shows it as text. The code is in `src/renderer/extensions-state.ts`, `extension-menu.ts`, `extension-form.ts`, `extension-actions.ts`, `extensions-ui.tsx` and `form-dialog.tsx`, and, for the trust, `src/main/extension-trust.ts`.

- **Tools menu.** A **Tools** button after Edit, shown only while the host has the `editorExtensions` capability and `ListEditorExtensions` says `enabled` (hidden for an older host and for a host started without `--editor-extensions`). Its items are `GetEditorUi`'s `menuItems`. A path like `Tools/Align/Snap...` becomes nested submenus: a leading `Tools` is dropped, empty segments are skipped, groups appear in the order they are first met, and the item's title is its label (two items with one label are two entries; the id names an item). A submenu replaces the level shown and has a **Back** item; the arrow keys work (Right enters, Left goes back). The menu is built each time it opens, and fetched again on `extensionsChanged`, after missed events and on a new connection.
- **Enabled or disabled.** `enabledWhen.selection` (`any`, `nonEmpty`, `one`, `none`) is checked against the hierarchy's selection; `componentType` means every selected object has a component of that type. An item is shown disabled, with the reason as its tooltip, when: its `minRole` is above yours (an editor and an admin-only item); the host is read-only, you are a viewer, a game is playing, no scene is open or the editor is busy; an edit group is open; another item is running; its extension is faulted (it stays listed until an admin reloads it); or the host speaks protocol 1.14 (it lists extensions but cannot run them). The host checks all of this again and is the authority.
- **Parameter form.** An item with a `form` opens a **FormDialog** (`form-dialog.tsx`): a modal with a row per field (number, int, string, bool, Vector3, GameObject, enum), drawn with the inspector's own field editors (a GameObject is picked from the scene's objects), the declared defaults, the tooltip as a hint, and the inspector's checks (`extension-form.ts`): a number with a min or max is clamped to it, an int must be whole, an enum one of its options. Text that is not valid blocks OK and says why next to the field. Enter in a field is OK, Escape and Cancel close it, Tab stays inside, the first field has the focus, the focus goes back afterwards, and a click outside does not close it (typed values are not thrown away). Hidden fields are not shown but are sent with their defaults. An item with a `confirm` question asks it first (a Cancel sends nothing).
- **Running an item.** As before an undo, the editor first sends what the inspector and hierarchy hold back, finishes a gizmo drag and ends its own edit groups (the host refuses an item while one is open, decision D9; one that cannot be ended refuses the run with a message). Then the confirm and the form, then `InvokeMenuItem` with the selection as it was when the item was chosen (at most 4096 objects), the form's params and the `uiRevision` of the menu the item came from. The button shows a spinner while it runs (the host bounds the time: there is no cancel) and every item is disabled. On success the answer's revisions are taken as the scene's, the host's events are polled so the hierarchy, inspector and history follow (the item is one undo step, named by its title), the objects in `select` are selected once the hierarchy has been read again, and the message and warnings are shown under the toolbar and noted in the console.
- **Errors.** `staleUiRevision`: the menu is fetched again and the person is asked to run the item again (nothing is retried by itself). `editGroupOpen`: finish the edit, then try again. `extensionFailed`: the host's own message (its changes were taken back, with no host path) and the panels follow. `extensionFaulted`: the extension is shown disabled, with a hint that an admin can reload it. `forbidden` and `readOnly` keep the host's code, so a read-only answer also makes the editor read-only. All of these go to the error banner and the console.
- **Console.** `extensionOutput` events (`Editor.Log`, Admin-only) are lines of the **Extension** source, registered in the console's source registry, with their level and the extension's name in front (`[Align Tools] text`). The host also logs each line as an Admin log line `extension <name>: <text>`; the editor drops that copy (for as long as 200 lines are pending), so a line shows once. The text is untrusted and is only ever a text node.
- **Trust, and the launcher flag.** The host loads extensions only when started with `--editor-extensions`, and the editor passes it for **a local project folder the user trusted, and only then** (decision D5). Opening a local project whose `editor/` folder has at least one `.lua` file shows a native dialog of the main process (the page cannot answer it) before the host starts: "This project contains N editor extensions", the file names, that they run code on this computer's editor host, that what each may do (its capabilities) is not known until the host loads it, and **Trust** or **Not now** (the default, and what Escape does). **Trust** is remembered for that folder and the host starts with the flag. **Not now** starts the host without it and shows a banner under the toolbar, "Enable extensions...", which asks again in the same dialog and then restarts the host (after asking about unsaved scene changes, since a restart discards them). A project with no `editor/` folder or no `.lua` file in it is never asked and never gets the flag; a remote host never gets it from the editor (its operator starts the host with `--editor-extensions`; the editor only shows what the host reports); a play host never gets it. Restarting the host never asks: a trusted folder gets the flag again, any other does not.
- **Where the trust is stored, and what it is keyed by.** In `extension-trust.json` in the editor's user data folder (beside `recent-projects.json`; its own file, because the recent list keeps ten paths and drops the oldest), written only by the main process after the user's answer. The key is the folder's **real path** (links, `..`, a trailing separator and, on Windows, the letters' case are resolved by the file system; lower-cased on macOS), so a moved, renamed or copied project, or another project, asks again and a folder that cannot be resolved is never trusted. It is folder-level trust, as in VS Code: a later `git pull` that adds an extension to a trusted folder runs on the next start without a new question. Nothing inside a project can say "trusted". The `editor/` listing the dialog shows is read in the main process by a bounded walk (8 levels, 4096 entries, the first 64 names listed, names only: a file's content is never read, and nothing is evaluated in Electron); a link or junction, a file or folder, is skipped and never followed, and an `editor/` that is itself a link has no extensions.
- **The Extensions section** (Project Settings, registered with `settingsSections.register`). Not connected, a host older than 1.14, and a host that cannot be asked say so. A host with extensions off explains how to turn them on: for a local project with extensions, the banner's path (with an **Enable extensions...** button); with no `.lua` in `editor/`, to add some and reopen; for a remote host, the operator's flag. With them on it lists each extension: name, state (loaded, failed, faulted), API version, the first 8 hex digits of its SHA-256 (the whole hash is the tooltip), capabilities, item count, and the host's error text (path-stripped by the host) under a failed or faulted one. **Reload** (`ReloadEditorExtensions`) is the admin's: disabled, with the reason, for another role, on a read-only host and during play; a refusal from the host is shown. For a local project it also shows the files, whether this folder is trusted and whether the running host was started with extensions, and **Forget trust for this project** (the running host keeps what it loaded until it restarts, and says so, with a **Restart host** button).
- **Not built:** inspector sections and buttons (E-X5, `InvokeInspectorAction`), hooks (E-X6), panels, gizmos and dynamic forms (deferred in the design). The editor cannot open or edit extension files (they are outside `assets/` by design). Extensions load at host start or on Reload only.
- **Not verified:** a real host running extensions and a real Electron window (the trust dialog is the main process's `dialog.showMessageBox`; the unit and DOM tests use fakes for the host and for the dialog's answer), and a round trip through `index.tsx`'s wiring (it runs only in the page).

## Undo, redo, edit groups and autosave

Protocol 1.6.0 (engine #78, PR #95). The history is the host's, not the editor's: it records every command that changes the scene, so the editor only asks it to undo and redo, and shows what it says. The commands are `Undo`, `Redo`, `BeginEditGroup`, `EndEditGroup`, `GetHistory`, `GetAutosave`, `RestoreAutosave` and `DiscardAutosave`; their answers (`EditResult`, `History`, `Autosave`) are validated before use (`src/protocol/edit-history.ts`), and the `historyChanged` event is parsed with the other state events.

- **Edit menu and shortcuts.** The toolbar's **Edit** button has "Undo <step>" and "Redo <step>" with the labels the host gives ("Undo Create Cube"), disabled when there is nothing to do. Ctrl+Z undoes, Ctrl+Shift+Z and Ctrl+Y redo (Cmd on macOS), except in a field that takes text, which keeps its own undo. `EditorStore.history` holds what the menu shows (can undo or redo, the two labels, the counts): it is kept current by `historyChanged` events, read with `GetHistory` on connecting (a host that is already running has a history) and after missed events, and cleared when the connection drops.
- **What runs before the host is asked** (`edit-controller.ts`, `EditController`). First what the editor holds back is settled: the inspector's pending edits (they wait 250 ms for more), a slider drag that is being ended, a delete, duplicate or move of several objects that is running, and a rename on its way. Only then are the edit groups still open ended (the host refuses Undo while one is open), so a value sent by that settling is inside its group. The history is read again, so an edit made a moment ago is a step to undo. Undo and redo are off while the editor is busy, not connected, has no scene or shows a play session (`EditorStore.canEdit`, `setPlayMode`; the host refuses them outside edit mode). Then `Undo` or `Redo` is sent and the host's events are polled at once, so the panels don't wait for the next poll. One undo runs at a time and one more may wait: a key that repeats while they do is ignored. The host's refusal ("Nothing to undo", a step that couldn't be undone, outside edit mode) is shown in the error banner.
- **The panels follow.** An undo is a `sceneChanged` like any edit: the hierarchy reads again and drops from the selection the objects that no longer exist; the inspector reads its object again when the event lists it. After an undo of a delete or of a component's removal the host restores a snapshot, which rebuilds every object, so the event says `full: true`: the hierarchy keeps its selection and expanded objects by UUID where they still exist, the inspector reads its object again and forgets what it learned about other objects' components. The answer's `revision` and `savedRevision` are taken at once.
- **Unsaved marker.** It is the one it always was: the scene is clean when `revision == savedRevision`. The host sets `savedRevision` to the new revision when an undo or redo brings the scene back to the state it was saved at, so the `*` goes (and comes back when the scene is redone away from it or undone past it). The editor holds no history of its own to decide that.
- **Edit groups** (`edit-groups.ts`, `EditGroups`) make one step of a gesture. A slider's drag in the inspector is one: the group opens when the pointer goes down on the slider, the edits made while it is held (sent every 250 ms) are merged by the host, and when the pointer is released or cancelled, or the window loses the focus, what is pending is sent and the group ends. Deleting, duplicating or moving several objects in the hierarchy is one step each ("Delete 3 objects"); one object is one step already and sends no group. A group is always ended: the end runs in a `finally`, an end is never sent before its begin was answered, a failure to end one is reported and tried again before the next undo, and a group the host refused just leaves the edits ungrouped. A group is ended by the handle `begin` gave, so a release that comes after Undo closed the drag's group can't close a group other work opened since, and Undo waits for running work (a multi-delete) to end its own group. The host ends a group its client left open when the connection closes and at the next `Hello`, so the editor only forgets its own count then.
- **History panel** (`history-panel.tsx`, `history-state.ts`, `history-jump.ts`; a tab beside the console, closable, from the Window menu). It lists the host's undo history from `GetHistory`, oldest first, under an "Initial state" row: done steps normal, undone ones dimmed, the state the scene is in marked, each step's memory on the row and the total (with the scene's revision and saved revision) at the bottom. The host reports a label and a size per step, nothing else: there are no per-step revision numbers, no saved-step marker and no group boundaries (an edit group is the single step the host merged it into, so a gizmo drag is one row). The host caps the history at 200 steps and 128 MiB, so the list is never longer and is not virtualised. It is read on opening, on every `historyChanged` event (debounced 100 ms) and after every jump, and the newest read wins. Clicking a row, or Enter on it, jumps there (`EditController.jumpTo`): the same settling as Undo (pending edits sent, open groups ended, history read), then `Undo` or `Redo` is sent as many times as it takes, one at a time, as one operation with a "step n of m" line and **Cancel** (Escape in the list does the same) honoured between steps; a typed Ctrl+Z meanwhile is ignored. It stops at the first refusal (the error is shown with how far it got), when the editor can no longer edit, and when the number of steps changes underneath it (another client edited); after any end the host's history is read again, so the list is always what the host has. The rows are disabled, with the reason shown, when not connected, on a read-only host or as a viewer, during a play session, while the editor is busy, while a client edit group is open (a drag in progress) and while a jump runs. Keys in the list: Up, Down, Home, End, Enter (or Space) to jump, Escape to cancel; only the active row is in the tab order. Closing the panel stops its listeners. A host `UndoTo` stays a later option if long jumps over snapshot steps prove slow.
- **Autosave recovery** (`autosave.ts`, `EditorStore.checkAutosave`). The host writes the open scene to `.n2/autosave/` while it has unsaved changes. When a scene is opened (the startup scene on connecting, **Open scene**, or another client changing it), the editor calls `GetAutosave`; an autosave there with no unsaved changes in the scene is what a crash left, and a dialog says which scene, when it was written and how large, with **Restore** (`RestoreAutosave`: one undoable step, so declining afterwards is one undo; everything refetches), **Discard** (`DiscardAutosave`) and **Decide later**. Until the user decides or saves, the host keeps the old file and writes no new autosave of that scene. It is asked once per scene per connection (opening the scene again asks again), and never for a scene that has unsaved changes, where the autosave is the running host's own copy of them (a page reload, say). A host before 1.6 has none to ask about. The question is also asked after New scene and Save as (the file they land on may have an autosave). It belongs to the connection and the scene: a connection that ends closes it (that is not an answer), and an answer given after another scene was loaded is not applied to that one, which is asked about instead. A failed restore shows the host's reason and asks again, so a bad file can be discarded. **Decide later** (or a failed restore) leaves the decision outstanding for that scene: the Edit button shows a dot and its menu has **Recover autosave...**, which asks again whatever the scene's unsaved changes. A `GetAutosave` that failed is not an answer: the scene is asked about again the next time it is fetched.
- **macOS.** The menu bar's Edit items own Cmd+Z there, so the main process sets an application menu (`src/main/app-menu.ts`, macOS only) whose Undo and Redo send a command to the page (`window.editMenu`), which runs the host's undo, or the focused text field's own. The Edit menu names the shortcut Cmd or Ctrl. Windows and Linux are unchanged: the page handles the keys.
- **Not here.** A play mode that calls `EditorStore.setPlayMode`.

## The assets panel

Protocols 1.9.0 and 1.10.0 (engine E8, PR #103; 1.10.0 adds play mode, which refuses the asset writers). The **Assets** panel (top left, `src/renderer/assets-panel.tsx`) replaces the old Files panel: the editor no longer reads or writes the project's files itself, every asset operation goes through the host (`ListAssets`, `GetAssetInfo`, `SetImportSettings`, `ReadTextAsset`, `WriteTextAsset`, `CreateScriptAsset`, `CreateFolder`), so a remote host would work the same. The logic is framework-free and tested in Node: `asset-tree.ts` (the listing as rows, filters, `res://` path helpers), `asset-edit.ts` (the checks before a request: names, import settings JSON, text files), `assets-state.ts` (`AssetsState`, the signals and actions), and `src/protocol/asset-parse.ts` (the validated answers); `assets-panel.tsx` is the DOM around them.

- **The listing.** One recursive `ListAssets` of the whole assets folder, shown as a tree (folders first, then files, empty folders too) with each asset's type, short UUID and size; a model opens to show its parts (sub-assets, `path#key`). Typing in the search box (path or UUID) or choosing a type switches to a flat list of matches. The full path, type and UUID are in the row's tooltip and in the detail below the list, where the UUID can be selected and copied. It is read again when an `assetsChanged` event arrives (also after the host's file watcher found a change made outside the editor), when events were missed, and by **Refresh**; reads asked for while one runs share one more read.
- **Detail and import settings.** Selecting a file reads `GetAssetInfo`: its size, modification time, whether the engine holds it in memory, and its import settings as JSON. **Apply** sends them with `SetImportSettings` after checking that they are a JSON object within the host's limits (64 KiB); the host's refusal is shown under the editor and the text stays. Settings you are editing are never replaced by a refresh; if the host's changed meanwhile the editor says so.
- **Drag to a field.** Dragging an asset (or a model's part) onto an asset slot of the inspector sets it when its resource type is the field's `assetType`; otherwise the slot says "X is a Texture; Font expects Font". The drag carries the asset's UUID, path and type (`drag-types.ts`). The slot's own search list uses the same listing (`asset-tree.ts` `assetEntriesOf`, through `InspectorState`).
- **Making things.** **+ Folder** and **+ Script** (and a folder's context menu: New Folder, New Script, New Scene) make them in the selected folder; a name is checked like the host checks it (no `/ \ : * ? " < > |`, no trailing dot, no Windows device name), then `CreateFolder` or `CreateScriptAsset` (the engine's script template; the host makes missing folders and says if the file exists). A new script opens in the editor.
- **The text editor.** Double-clicking a `.lua`, `.json`, `.txt`, ... file (any extension `ReadTextAsset` takes, but only files the host indexed are listed) opens it in a tab of the bottom panel. **Ctrl+S** (or the Save button) sends `WriteTextAsset`; the host writes exactly the text, a byte order mark and line endings included. A script an object holds is reloaded by the host: when the new script fails, that is a log event, not an error response, so the tab shows the error-level log lines that arrived after the save, and the console has them. A refused save (the open scene's file, too large, a NUL) keeps the text and says why. Line endings are kept: the editor holds LF (a textarea can't hold CRLF), and the file's own style (the majority one for a mixed file, which is made uniform on its next save) is put back when it is written; a tab is only changed when its text is. A file changed outside the editor shows the new text in a tab without edits; with unsaved edits the tab says so and offers to discard them and reload. Closing a tab with unsaved changes asks first, and so do closing the project and the window.
- **Not here.** Moving, duplicating, deleting and thumbnails (post-MVP in the plan: a move changes the UUID). Only files the host indexes are assets: a file whose extension has no registered loader (`.txt`, `.json`) is neither listed nor watched, so the panel can't open it (the host's `ReadTextAsset` would take it by path). While a play session runs (`store.playMode`) the panel's editing is off: creating, Apply and Save are disabled, since the host refuses them.
- **Not verified against a live host yet** (the engine host does not build on the development machine): the DOM, the layout, and the drag; the logic and the client's requests and answers are tested.

## Typed import settings (FE10)

A **Texture**, **Model** or **Font** asset shows its import settings as a form in the assets panel's detail instead of raw JSON (roadmap section 6, decision U7). The tables are client-side (`src/renderer/assets-import-schema.ts`) and mirror the engine's parsers, which no command describes: `texture` {`srgb`, `filter` linear/nearest, `wrap` repeat/clamp, `mipmaps`, `flipY`} from `Texture::ParseSettings`; `model` {`scale` > 0, `importMaterials`, `generateNormals`/`generateTangents` never/ifMissing/always, `pbrMaterials`, `mergeSubmeshesByMaterial`} from `Model::ParseSettings`; `font` {`basePx` 4-256, `spreadPx` integer 1-32, `paddingPx` integer 0-16, `charset` ascii/latin1, `extraChars`} from `Font::ParseAtlasSettings`. Defaults are the engine's struct defaults (`TextureSettings`, `ModelSettings`, `AtlasSettings`); a test pins every key, kind, default and choice, so a change in the engine must be made here too.

- **The JSON stays the truth.** The form reads the settings text and writes each change back into it; an empty field or "Default (...)" removes the key, so the engine's default applies. Keys the form does not know are kept and sent back: unknown keys of the type's block are listed, everything outside it is shown read-only under **Other (JSON)**. **Edit as JSON** switches to the old text editor and **Edit as form** back (off while the text is not a JSON object). Other asset types keep the JSON editor only.
- **Checked before Apply.** A value the engine would ignore with a warning (wrong type, out of range, an enum name in another case, a block that is not an object) is shown at its field and keeps **Apply** off; `AssetsState.applySettings` checks it again, also for settings typed as JSON. A font spread larger than half the base size is a warning only: the engine lowers it itself. **Revert** puts the host's settings back.
- **Apply** sends the whole object with `SetImportSettings` (a replacement); the host saves the `.meta` and drops the loaded asset, so its next use reimports it with the new settings.
- **Gating.** The fields and Apply follow `canWrite` (a play session, a read-only host or a viewer role disables them and the reason is shown). Ctrl/Cmd+S (`assets.applySettings`) applies from a form field as it does from the JSON text.
- **Not here:** previews and thumbnails (they need the engine's `GetAssetPreview`, EN1), editing several assets at once, and audio settings (the engine reads none).

## The viewport

Protocol 1.7.0 (engine E7a) and 1.8.0 (E7b). The **viewport** (`src/renderer/viewport-panel.tsx`) shows the editor view: the open scene seen from the editor camera, which the host owns (`SetEditorCamera`, `GetEditorCamera`; it is not a scene object, is not saved and is not part of undo). The scene view skips the screen-space UI pass (a confirmed decision of #6). Everything with logic is framework-free and unit tested in Node; the panel is DOM glue.

- **Frames on demand.** There is no render loop. `FrameScheduler` (`viewport-frames.ts`) asks with `RenderFrameIfChanged(sinceRevision)` once on connecting, when this client changed the view (the camera moved, the viewport was resized) and when the host says it changed (the `frameChanged` event, or a `sceneChanged`, polled with the other events). Asks are coalesced to one in flight and one waiting, on the next animation frame; an answer with `modified` false (a few bytes) leaves the picture. An idle viewport sends nothing. Frames are RGBA, top row first, drawn as they arrive; the host's viewport is sized to the panel in device pixels (`SetViewportSize`, `viewport-size.ts`) and shown 1:1.
- **Camera** (`viewport-camera.ts`, pure maths, the client computes the pose and sends it, as the plan decided). **Alt+left drag** orbits, **middle drag** pans, the **wheel** zooms (toward the target, by a fraction of the distance), **hold the right button** to look, and fly with **W A S D** (**Q** and **E** down and up, **Shift** faster), **right button + Alt** drag dollies. **F** (or the Frame button) frames the selected objects. The pose is an orbit around a target, so orbiting and zooming keep the point of interest. On connecting the camera starts where the host's is (`GetEditorCamera`). Poses go out through `LatestWinsSender`: one `SetEditorCamera` in flight, the newest wins, so a drag costs one request per frame at most. The View / Gizmos menu switches perspective/orthographic projection, six axis views, and 2D mode (front orthographic, rotation locked, pan/zoom only). Numpad 1/3/7 selects front/right/top, Ctrl selects their opposites, and Numpad 5 toggles orthographic. Align view to selected uses its world orientation. Save nine camera bookmarks per scene with Ctrl+Shift+1..9 and recall with Shift+1..9; poses and projection are stored per project. Leaving 2D mode restores the previous view. The mapping from mouse and keys to actions is `viewport-input.ts`.
- **View overlays** are saved per project in View / Gizmos: a fading grid, selected or all Box/Sphere/Capsule colliders, all-object bounds, light/camera icons and point/spot light ranges. They draw through objects because the overlay canvas has no depth buffer. Entity geometry is cached by scene revision, capped at 256 unique objects (selection first), with at most four reads in flight. Larger scenes show the first bounded set. Grid geometry and collider geometry use the editor camera in both projections.
- **Translate gizmo** (`viewport-gizmo.ts`, `viewport-controller.ts`). Drawn and hit-tested on the client, on a canvas over the frame, from the camera matrices (computed in `viewport-math.ts`, the protocol's conventions) and the selected object's `worldMatrix` and local transform (`GetEntity`). Three arrows and three plane squares (XY, XZ, YZ) at a constant size on screen, along the world's axes (or the primary object's own, in local space: see the toolbar). A square sits between its two axes on the side that faces the camera, fades as its plane turns edge-on and is hidden (and can't be grabbed) below about 7 degrees; an arrow within reach of the pointer is taken before a square. An arrow drag moves along its axis (the pointer's ray against the axis line), a square drag in its plane (the ray against the plane), so the objects stay under the cursor; the move is shown at once on the client, and sends `SetLocalTransform` (the local position) inside one `BeginEditGroup`/`EndEditGroup`, so the drag is one undo step ("Move <name>"). At most one move is in flight (the newest wins). **Ctrl** snaps (see the toolbar below: by default to 0.5, relative to where the drag began, along each axis the handle moves along), **Esc** puts the object back (the group still holds the move and the move back, and the host's `FinishGroup` skips only a group with no edits, so a "Move" step that changes nothing is recorded: the scene shows as changed and redo is cleared). The gizmo is placed on the primary selection and moves the whole selection: every selected object goes by the same world delta, each turned into its own local position through its own parent chain, and only the topmost selected objects are moved (an object under another selected one moves with it, never twice). A "Move N objects" group holds them all, so the drag is one undo step. A drag sends one batch of `SetLocalTransform` calls at a time (the calls of a batch together, the newest positions winning). A failure is reported once per object; an object the host says is not found is left out of the rest of the drag, one that failed otherwise is tried again with the next move, and Escape puts back every object that was moved. A drag is abandoned (nothing more is sent, silently) when the connection goes or when the host says another scene was loaded (`sceneChanged` with `full`, counted as `EditorStore.sceneReplacedCount`); a full change that only means "too many objects to list" is the drag's own echo and changes nothing until the drag ends. The targets are read again only for the selected objects a change names (with at most 16 reads in flight), everything on a change of the selection, and a press while they are for another selection starts no drag. The selection and scene-change wiring is `viewport-selection.ts`. The gizmo is shown only while the scene can be edited, and Undo and redo first finish a drag in progress (the host refuses them while its group is open), the camera is frozen while a handle is dragged, and a drag in flight is dropped when the connection goes or another scene replaces the scene. Both kinds of drag ignore a pointer ray that meets the axis or plane behind the camera or beyond the far plane and cut one update's jump to 50 handle lengths (a ray nearly parallel to a plane is rejected too). The handles, their pick distance and the click slop are CSS pixels, scaled by devicePixelRatio. The world move becomes a local one the way the engine combines transforms (`Transform::Combine`: position = pPos + pRot*(pScale*lPos), not a matrix product): the object's parent's world matrix is read too (`GetEntity` on the parent, once per load) and the local change is its inverse linear part applied to the world move, which is exact whatever the signs of the scales (a mirrored parent or child, a child with a zero scale on one axis). Only if the parent can't be read is the parent derived from the object's own world matrix, taking each axis's sign from the object's own scale; that is right for a mirrored child and wrong for a mirrored parent with a rotated child. The matrices are computed locally for zero latency; after the viewport is sized, the editor compares them once with `GetEditorCamera`'s and writes a console warning if they differ.
- **Tools: move, rotate, scale, none** (FE3; `ViewportController.mode`, `GizmoMode`). The gizmo has a tool: Move (the translate gizmo above, the one at start), Rotate, Scale, or none (select only: no gizmo, and a press where a handle would be is a plain click). **W**, **E**, **R** and **Q** choose them (keymap actions `gizmo.translate`, `gizmo.rotate`, `gizmo.scale` and `gizmo.none`, scope viewport, physical keys, rebindable); while the right button is held W, E and Q fly the camera as before (the fly keys keep their priority) and R, which is not a fly key, still chooses Scale. The tool can't change during a drag (the key is left alone), is shown by the toolbar's buttons and read out as "Tool: Rotate (E)" in its status line, and is remembered per user (see the toolbar). A press, a hover and a drag work on the current tool's handles only, and only while the scene can be edited (the translate gizmo's guard: no gizmo in a read-only host, a viewer's session or play mode). The space, the pivot and the snapping are the toolbar's (below).
- **Rotate gizmo** (`viewport-rotate.ts`). Three rings, one per axis (the world's, or the primary object's own in local space), around the pivot (the primary object's origin, or the selection's centre), drawn on the overlay at the same constant size on screen as the arrows (a ring's radius is 0.85 of a handle length). The half of a ring on the camera's side of the pivot is strong and the only part that can be grabbed; the far half is faint; the nearest ring within 8 CSS pixels of the pointer wins. A drag measures the angle the pointer's ray has turned about the ring's axis in the ring's plane (the hit point's angle about the pivot, so the grabbed point stays under the cursor), unwrapped, so a drag can go past half a turn and round more than once. When the ring's plane is within about 12 degrees of edge-on to the ray (|cos| to its normal below 0.2) the angle would explode, so the drag follows the pointer along the ring's on-screen tangent at the grab point instead (the motion along it over the ring's on-screen radius is the angle); the choice is made when the drag begins and kept. Every selected object (the topmost, as for a move) turns about the shared pivot (the primary's origin, or the selection's centre with the toolbar's Center): its world position becomes `pivot + R (p - pivot)` and its world rotation `R q`, turned into local values the way the engine composes (the world rotation is `parent rotation * local`, so the local one is `parent^-1 * R * parent * local`, keeping the sign of the old quaternion; the position as the translate gizmo does, through the parent's world matrix) and sent with `SetLocalTransform` (a quaternion, so no Euler drift; scale as it was; an object at the pivot keeps its position untouched). The parent's rotation is read from its world matrix (columns divided by their lengths), or derived from the object's own matrix when the parent could not be read. A parent with a scale of zero, or a mirrored one (an odd number of negative scales, which a matrix can't attribute to an axis), can't be turned through: the object is reported once and left out of the drag while the others still turn; a parent with two negative scales reads as its rotation turned half a turn (the same matrix), so a child's turn about some axes can go the other way. Ctrl snaps the angle (by default to 15 degrees). The angle is shown beside the gizmo while dragging ("Z +37.5 deg"). The selection box is left off during a rotate or scale drag (the host's boxes are world-aligned boxes of the old pose) and is read again when it ends.
- **Scale gizmo** (`viewport-scale.ts`). Three handles with a cube at the end and a square at the centre for uniform scale, at the same constant size. Scale is always local (the roadmap, as in Unity): the handles point along the primary object's own axes (the columns of its world matrix, scale stripped), because the local scale they change is along those. A drag is a ratio, 1 where it began. An axis handle's is `1 + (t - t0) / max(t0, 0.3 handle lengths)`, where t is where the pointer's ray meets the axis now (the nearest point on the axis line, as for the translate arrows) and t0 where it met it at the start, which is `t / t0` unless the drag began near the pivot (so a grab there doesn't jump); the centre's is signed, `1 + m / (half the gizmo's size)` with m the pointer's motion since the grab along the screen's up-right diagonal (up and right grows it, down and left shrinks it). The ratio is clamped to 0.001 .. 1000: a drag that shrinks it far enough stops at 0.001 and never flips the sign or makes a degenerate matrix. Every selected object's local scale is multiplied by it along the handle's axis (its own x for the x handle; an object that is already mirrored stays mirrored, a zero scale stays zero), and the centre handle multiplies all three and scales the objects' offsets from the shared pivot too (an object at the pivot keeps its position). Ctrl snaps the ratio (by default to 0.1), never to zero. The ratio is shown while dragging ("X x1.25").
- **Viewport toolbar** (FE4; `viewport-toolbar.tsx`, over the picture in the viewport panel; the maths in `viewport-snap.ts` and `viewport-tool-settings.ts`, the state on `ViewportController`: `mode`, `space`, `pivot`, `snap`). Buttons for the four tools (Move, Rotate, Scale, Select; the active one is pressed, the tooltips name the current chord from the keymap, so a rebinding shows), a **Space** toggle (World or Local) and a **Pivot** toggle (Pivot or Center), then a snap checkbox and an increment per tool, and for a move a Relative or Grid choice. Keymap actions `gizmo.space` (**X**) and `gizmo.pivot` (**Z**), scope viewport, physical keys, rebindable, left alone during a drag and while a game is live. A screen reader hears the tool from a status line ("Tool: Rotate (E)"), which replaces the old text label. Every control is disabled while the scene can't be edited (read-only host, viewer, play mode: the gizmo is not there either).
  - **Space.** In local space the move arrows and planes and the rotate rings follow the primary object's own axes (its world matrix's columns with the scale stripped: approximate under a sheared parent chain). The scale handles always follow the object's own axes, so the Space button is disabled for Scale and Select; the Pivot button is disabled for Select. A move along a local axis snaps the distance along that axis, so it stays on its line; every selected object goes by the same world delta.
  - **Pivot.** Pivot is the primary object's origin. Center is the centre of the union of the selected objects' bounds (the boxes `GetEntityBounds` gave for the selection box); with no box (a host that can't measure the object) it is the primary's origin, so the gizmo never goes missing. The gizmo sits there, and rotation and a uniform scale turn about it. The space and pivot can't change during a drag.
  - **Snapping.** Each tool has a toggle and an increment; the defaults are the roadmap's U4: move 0.5, rotate 15 degrees, scale ratio 0.1, all off. A move snaps RELATIVE by default (the drag's component along each handle axis is rounded, so the object keeps its offset from the grid) or to the absolute world grid (Grid: the pivot's world position along each world axis the handle moves along is rounded; only for world-axis handles, a local-axis handle stays relative). A rotation is rounded as a total angle, so it keeps snapping past half a turn or a full one. A scale ratio is rounded and never goes below one step. **Ctrl inverts** the tool's toggle for the drag: with the toggle off Ctrl turns snapping on (as it always did), with it on Ctrl turns it off; pressing or releasing Ctrl mid-drag takes effect at the next move. A step is a number from 0.0001 to 100000 (a move), 0.01 to 180 degrees (a rotation) or 0.0001 to 1000 (a scale); a field with text that is not one is marked invalid and changes nothing, and gives the setting back when it loses the focus. The rounding is not fooled by floating point (3 x 0.1 is 0.3, never -0). A drag keeps the settings it began with.
  - **Remembered** through the preferences store (`viewport-tool-prefs.ts`): the tool, space and pivot per user (`viewport.tool`); the snap toggles, increments and kind per project (`viewport.snap`, the roadmap's "stored per project", since a grid that suits one project's scale does not suit another's). Each value is validated field by field: a missing, wrongly typed or out of range field takes its default, damaged storage gives the defaults, and unusable storage never throws.
  - Not verified live: how the gizmo, the toolbar's layout and the snapping feel in a real viewport.
- **One undo step, the same for all three tools** (`viewport-drag.ts`: `TransformDrag`, which `GizmoDrag`, `RotateGizmoDrag` and `ScaleGizmoDrag` extend). A drag is one `BeginEditGroup`/`EndEditGroup` ("Move Cube", "Rotate 3 objects", "Scale Cube") around at most one batch of `SetLocalTransform` calls in flight (the newest wins); a failure is reported once per object, an object the host says is not found is left out of the rest of the drag, Escape puts every changed object back exactly (position, rotation and scale as they were read) with the group still ending once, a release that changed nothing sends nothing, and a drag abandoned by a lost connection or a replaced scene sends nothing more and asks for no frame.
- **Not verified against a live host yet**: the feel of the rotate and scale handles (ring picking, the tangent fallback near edge-on, the scale ratio's sensitivity), how they look, and the tool keys in a real window; the maths, the drags against a fake engine and the key handling are tested.
- **Picking, framing and the selection box** (protocol 1.8.0, engine E7b, PR #100; `viewport-picking.ts`, `viewport-controller.ts`). `createPickBackend` wraps `PickEntity` and `GetEntityBounds` as the controller's `PickBackend` seam (kept so the controller is tested with fakes; with no backend a click selects nothing, there is no box and Frame looks at the object's position). **Click to select.** A press that is released within the click slop (4 CSS pixels, scaled by the pixel ratio) and did not begin on a gizmo handle is a click; the pointer's position becomes a frame pixel (`framePixelOf`: top-left origin, y down, the canvas's on-screen rectangle scaled to the frame's device pixels, fractions kept) and `PickEntity` is asked (`includeInactive` false), on click only (no hover pick). A press on a handle is the gizmo's even when no drag can start from it, so it never selects what is behind the gizmo. A point outside the frame is a miss and is not sent. One pick is in flight; clicks meanwhile wait and only the newest is asked (`LatestWinsSender`), and an answer is applied only for the newest click, on its connection, and when the selection is still what the click was made over (a later click, a miss outside the frame or a selection made in the hierarchy meanwhile makes it stale). While the host's viewport was resized after the picture on screen was rendered, the pixel is mapped exactly to the host's size (`remapToHostViewport`: the vertical field of view is fixed, so offsets from the centre scale by the heights' ratio; one that falls outside the host's viewport is a miss). Nothing is asked without an open scene or from a host before protocol 1.8.0 (`hostHasPicking`), so such a click raises no error. The answer goes to `HierarchyState.pick`, which acts like a click on the object's row after expanding its ancestors: a plain click selects just that object, **Ctrl** (or Cmd) and **Shift** both add or remove it (as in Unity's scene view: there is no hierarchy range in a 3D view), and a click on nothing clears the selection (with Ctrl or Shift held it keeps it). The host picks a world canvas's graphic, never the canvas, and never an overlay canvas's elements, so a click on a button selects that button's object; select a canvas from the hierarchy. **Frame** (F) asks `GetEntityBounds` for the selected objects (one call) and fits the union of the boxes; with no boxes (an object without a transform, overlay UI, a host error) it falls back to the primary object's world position at a fixed distance. **Selection box.** The world AABB of every selected object (a group's is the union over it and its active descendants, so it frames the group) is drawn as its 12 projected edges on the overlay (each edge is clipped against the near plane in clip space, so a box the camera is inside, or with a corner behind the eye, still draws what is in front), in one `GetEntityBounds` call for the whole selection (`reloadBounds`: one read in flight, a request meanwhile makes one more read, and an answer is out of date only when the selection or the connection changed, so a storm of scene events can't starve the boxes; every change of the scene reloads, unfiltered, because an event names only what changed and a reparent into or out of a selected group changes its box). It is read again when the set of selected objects changes (not only the primary or the topmost, `followViewportSelection`), on every `sceneChanged` (also a `full` one: a gizmo drag's own echoes with more than 256 ids arrive as `full: true`, so `full` does not mean the scene was replaced; the box of a group changes when a descendant changes, and an event names only what changed), on connecting, and when a drag has ended. During a drag the boxes move with the pointer, and the drag's echoes cause no read.
- **Not verified against a live host yet** (the engine host does not build on the development machine): the camera conventions (the maths follows the protocol's description), the feel of the controls, and the drag over a real scene.

## Audio

The editor host runs headless, so its audio is mixed on an OpenAL loopback device and streamed to the editor rather than played by the engine. The editor plays it:

- It polls `GetAudio` every 25 ms (timed from the previous response, so requests never overlap), independently of the viewport's frame requests. It shares the connection with them, though, and the server answers one request at a time in order, so a `GetAudio` sent while a frame renders waits for it: frames slower than the buffer's slack (about 90 ms) can cause underruns. Each response holds everything mixed since the previous one (at most 250 ms), 48 kHz stereo, float32 or int16.
- The samples go into a jitter buffer that keeps about 100 ms scheduled ahead of playback, on a 48 kHz `AudioContext` (scheduled `AudioBufferSourceNode`s). Audio therefore trails the rendered frames by about 100 ms.
- The server mixes by its own clock and the sound card plays by its own, so the buffer slowly drifts. The buffer level is smoothed over chunks (an exponential moving average); when it leaves a ±20 ms band around the target, each chunk is resampled by at most 0.1% until it is back within 10 ms. If it runs dry (an underrun) or the server reports `droppedFrames` (we fell more than 250 ms behind), the buffer restarts at the target. Both are logged to the console and counted in the toolbar.
- **Mute** in the toolbar mutes or unmutes it, and the setting is remembered. The window allows autoplay, but if the `AudioContext` is still suspended the button reads **Enable audio**; click it to start playback.
- The toolbar shows the audio state: how much is buffered, `muted`, `none` when the engine isn't on a loopback device (`GetAudio` returns an error and the editor stops asking), or an error. Playback stops on disconnect.

The decoding and jitter-buffer logic is in `src/audio-stream.ts` (no DOM or Electron dependencies); the Web Audio side is `src/renderer/audio-player.ts`, in the page. The main process decodes each `GetAudio` response to float32 and the samples reach the page through `window.engine.getAudio`.

## Play mode

Protocol 1.10.0 (engine E9, PR #102). **Play** in the toolbar runs the open scene as a game in a second `N2EditorHost` process; the editor host is never touched by it, so its scene, undo history and unsaved changes stay as they were, and a script that crashes or hangs takes down only the game. The main process owns that child, as it owns the editor host (`src/main/play-session.ts`, `PlaySession`).

- **Starting.** `WritePlaySnapshot` on the editor host writes the open scene as it is in memory (unsaved changes play; nothing is saved and no revision moves) to `.n2/play/<name>-<hash>.scene`. The editor then launches `N2EditorHost --project <same folder> [--renderer <same>] --port 0 --token-env N2_EDITOR_TOKEN --play <file> --exit-on-disconnect --exit-on-stdin-eof` with a fresh token in that child's environment only, reads its ready line, connects a second `EngineClient` (Hello) and asks `GetPlayState`. Before it, what the editor still holds back (a rename, the inspector's 250 ms debounce) is sent, as Ctrl+S does, so the snapshot has the latest edits. The snapshot is deleted once the child is up, or when the start fails or is cancelled, only if it is a `.scene` directly in the project's `.n2/play` folder. A snapshot the child refuses ends it with `N2EditorHost --play: <reason>` before any ready line: the reason is shown. `renderer` in `settings.json` (`opengl` or `software`) is passed to every host as `--renderer`, and the child gets the value its editor host was launched with; without it the host picks its own.
- **States.** The toolbar shows Starting, Playing (frame and time), Paused, and what ended it: the game quitting (exit code 0, a note in the console), a crash (exit code and the child's last output lines, in the console and on the error banner) or a failure to start (snapshot, launch or connect, in the console and on the banner). The launcher owns Starting and Exited; the child answers Playing or Paused, and the toolbar asks it every 250 ms and when a `playState` event arrives, since a game can pause itself.
- **Pause, Step, Stop.** `SetPaused`; `Step` runs 1 frame of a paused game (the engine takes 1 to 1000); Stop sends `Shutdown`, waits 2 s and kills the child. The child also goes when the editor host's connection ends (a stopped, restarted or crashed host, a project closed or a page reload), when the editor quits, and (`--exit-on-disconnect`, `--exit-on-stdin-eof`) if the editor itself dies.
- **The view.** While a game is live the viewport shows its frames: `RenderFrame` is asked for again as soon as one is shown, at the display's rate (`RenderFrameIfChanged` is an editor-view command a play host refuses), after `SetViewportSize` on the child's connection. A frame that fails while the game still runs is asked for again (three times in a row, 200 ms apart) before the picture is given up on. The editor camera, gizmo, selection box and picking are off; when the game ends the renderer is restarted on the editor view, sized and rendered again from scratch (`FrameTarget`, `viewport-renderer.ts`), whatever stopped the game's frames. A child that doesn't answer its first request after Hello within 10 s fails the start.
- **Input** (`src/renderer/play-input.ts`). While the viewport has focus, keys, mouse buttons, the pointer and the wheel go to the game with `SendInput` instead of to the editor: `KeyboardEvent.code` becomes the engine's key name (`KeyW` is `W`, `Digit1` is `Key1`), the pointer is in frame pixels, top-left origin, and the wheel in lines. Key repeats are one press, a run of pointer moves is its last position, and one `SendInput` of at most 1024 events is in flight at a time. Losing focus (blur, the window deactivating) sends `releaseAll`. **Ctrl+Esc** leaves the game view, and Tab is not sent to the game, so a keyboard user can always move the focus out. The page checks every event before it reaches the child (`src/protocol/input-events.ts`), and can reach the child only through the commands of `PlayCommandArgs`: frames, audio, events and input. Gamepads aren't forwarded (the engine doesn't take them yet).
- **Audio and console.** The game's own `GetAudio` stream replaces the editor host's while it is live (the player starts over on the new source, and the editor host's audio comes back when it ends). The child's log lines are polled with `PollEvents` (about every 100 ms) and join the console with a mark on the left; its `playState` events refresh the toolbar.
- **Read-only.** For as long as a game starts or runs, `EditorStore.playMode` is set: the inspector is read-only (#6 decision 13), the hierarchy shows but doesn't change (no create, rename, move, duplicate, delete or active toggle, no drag; selecting and expanding work), the script editor is read-only, and New scene, Open scene, New script and Recover autosave are refused with a message. Undo and redo are off (`canEdit`). The edit host stays connected, but the editor sends it nothing that edits. A panel that edits anything else (the assets panel) should check `store.canEdit`.

The state machine is `src/main/play-session.ts` and the page's side is `src/renderer/play-controller.ts` (`PlayController`); both are unit tested with fakes. The page reaches the game through `window.play` (`PlayApi` in `src/shared/api.ts`).

## Read-only hosts

Protocol 1.11.0 (engine #126, `N2EditorHost --read-only`). This editor speaks 1.16.0 (`PROTOCOL_VERSION`, generated from the engine commit in `engine-ref.txt`) and still works with a 1.10 or 1.11 host, whose answers end before the newer fields (they decode to their defaults: not read-only, no error codes, no user, no role).

- **What the host says.** A host started with `--read-only` answers every command that is not a read with a refusal (`SetComponentFields`, `OpenScene`, `Undo`, `WritePlaySnapshot`, `Shutdown` and so on; the viewport camera and the viewport size are reads). `ServerInfo.readOnly` (read from Hello) says so up front. The editor asks for error codes in Hello (`errorCodes: true`), so a refusal arrives as `ErrorCoded` (message and code `readOnly` or, for later per-user roles, `forbidden`) and rejects with an `EngineError` whose `code` is set; a 1.10 host, or any other failure, sends a plain `Error` and the `code` is `undefined`. An unknown code is treated like a plain error.
- **The badge.** While `ServerInfo.readOnly` is true (`EditorStore.hostReadOnly`) the toolbar shows a **Read-only** badge.
- **One guard for writes.** `EditorStore.readOnlyReason` is why nothing can be written now (a play session, else the read-only host), `canWrite` is whether it can, and `canEdit` includes it (undo, redo, the gizmo). The panels read these instead of `playMode`, and `write-guard.ts` pushes the reason into the inspector and the hierarchy, so a new write affordance has one place to be disabled. Disabled, not hidden: the inspector's fields and buttons, the hierarchy (create, rename, reparent, duplicate, delete, drag and drop, the active checkbox), the assets panel (new folder, script and scene, the import settings, saving a text file), New, Open, Save and Save as, Play, and Edit > Recover autosave (a read-only host's autosave is not asked about either). Undo and Redo go with `canEdit`. Selecting, expanding, the viewport camera, picking, the console and reading files still work.
- **A denial that still arrives** (a command the editor did not know to disable, a `forbidden` role) is shown in the error banner with the host's own message, like any failure. The host refused the command whole, so nothing was applied: the inspector's and the hierarchy's optimistic values go back to the host's, and a `readOnly` one also makes the store treat the host as read-only until the connection changes (`EditorStore.deniedAsReadOnly`).
- **Over IPC.** The code is carried as `IpcResult.code` and, because the context bridge rebuilds a thrown error from its message alone, also as a prefix of the page error's message between two invisible marks (see `ipcError`, `errorCodeOf` and `errorTextOf` in `src/shared/api.ts`; the panels show the text without it). The access token is never part of an error.
- **Not verified:** the Electron UI against a live `--read-only` host (the unit and DOM tests use fakes).

## Users and roles

Protocol 1.12.0 (engine #130, `N2EditorHost --tokens-file`). A host that more than one person reaches has one token per user, each with a role, instead of one shared token.

- **The User field.** The remote forms (SSH tunnel and Direct address) have an optional **User** next to the token. It is sent in `Hello` as the trailing `user` string, only when it is not empty: with none, the field is left out of the payload, so an older host sees the `Hello` it has always accepted. It is not secret: the SSH form's recent remotes remember it with the other settings (the Direct form has no recent list, so it is typed each time), and the token is still asked every time and never saved or logged. A host started with `--token-env` or without a token ignores it. The user name has letters, digits and `. _ @ -`, up to 64 characters (what `N2EditorHost --new-token` accepts).
- **Who the host says you are.** `ServerInfo.user` and `ServerInfo.role` (`admin`, `editor` or `viewer`) are shown in the toolbar next to the Read-only badge, as `alice (editor)` (`EditorStore.hostUser`, `hostRole`). A host without a tokens file answers user `""` and role `admin`, shown as nothing; `--token-env` answers user `token`, role `admin`. A host before 1.12 sends neither, which decodes to `""` and counts as `admin`. A role this editor does not know is treated as a viewer, the safe side: the host enforces its own roles and this only decides what is offered.
- **Viewer.** A viewer can only look and may not play. It goes through the same guard as a read-only host (`EditorStore.hostReadOnlyReason`, so `hostReadOnly`, `readOnlyReason`, `canWrite`, `canEdit` and `write-guard.ts`): every write affordance is disabled with the reason "you are signed in as a viewer", Play included, and the Read-only badge shows.
- **Editor.** An editor can change the project. The one thing it cannot do is `Shutdown` the host, and the editor offers no way to send it to a remote host (Stop host is only for a host the editor launched itself, whose token is an admin's).
- **A `forbidden` denial** (a command the role does not allow that the editor did not know to disable) is shown in the error banner with the host's own message, and the edit is put back. It does not turn the whole editor read-only: only a `readOnly` denial does that.
- **Not verified:** the Electron UI against a live host with a tokens file (the unit and DOM tests use fakes).

## One session at a time: a busy host and a taken-over session

Protocol 1.13.0 (engine #176 and #177, pre-auth slots). A host serves one editor session at a time. A second client whose token is right replaces the session when it is the same user and role (takeover) or has a strictly higher role (admin over editor over viewer, preemption); otherwise it is turned away after up to a second with the error `busy`. A host without a token lets the newest connection take over.

- **Busy.** A Hello answered with ErrorCoded `busy` (the editor always asks for error codes) rejects `EngineClient.connect` with a `HostBusyError`, a different class from `HelloError` (a wrong token or an incompatible version): the token was right, so nothing is forgotten and no credential is asked for again. The code is the contract. The host's text names the role that holds the host (`a viewer session`); only one of the three role words is taken from it, for the message `The host is busy with another session (a viewer session)`, and any other text is not shown.
- **Retry.** The connect screen shows that message with `It will try again in N s`, and tries again by itself with a capped exponential backoff (1, 2, 4, 8, then 15 s, each cut by a random amount of up to half) for about two minutes, then stops and offers **Retry** (which starts over). **Cancel** stops it at once. The retry (`EditorStore.connectDirect`, `connectRemote`; `connect-retry.ts`) calls the same connect again with the same settings and token, which are held in memory only until it connects, fails otherwise, is cancelled or the connect screen is left; the token is never saved, logged or shown. A wrong token, a pin mismatch, an unreachable host or any other failure is shown once and never retried.
- **A session the host closed.** When another session takes the host over, the host closes the old session the way it closes any: no message comes first, so the editor can't tell it from a dropped connection. The editor shows `The host closed the connection` with a hint that another client may have taken the session over, and a **Reconnect** button, which returns to the remote connect screen (the token is asked for again). It does not reconnect by itself: that would take the host back from the other session and the two would fight over it.
- **Not verified:** any of this against a live host (the tests use stand-ins; the engine's issue #149 tracks the live check).

## The layout and the Window menu

Roadmap phase F1 (issue #6's UI roadmap, decisions U1 and U2). The editor's panels are entries of a small registry (`src/renderer/layout/`), not hand-placed components, so a new panel is one more `register` call in `builtin-panels.tsx`. The default arrangement is the one the editor always had (assets on the left, the viewport over the console and text files in the middle, hierarchy, inspector and engine stacked on the right); the DOM and CSS keep its structure, so the default looks as it did. There is no docking library and there are no floating windows.

- **Registry** (`panel-registry.ts`, framework-free). A panel is `{id, title, icon, component, defaultRegion, defaultGroup, closable, singleton, minSize, tabBar, unmountWhenHidden, sizing}`. The id is what a saved layout names, so it never changes. The six panels: `assets`, `viewport`, `console`, `hierarchy`, `inspector`, `engine`. Only the **viewport** can't be closed (a stale layout can never hide it). `singleton: false` is refused: one instance per panel is all that exists.
- **Regions and stacks.** Four regions (left, centre, bottom, right). Each holds one or more **stacks** top to bottom (the right region starts with three), and each stack is a row of tabs with one shown. A stack of one panel that has a header of its own (hierarchy, inspector, engine, assets) or is the viewport shows no tab bar, as before; the console always has one, as before; two or more tabs get a bar. Text files opened from the Assets panel are tabs of the bottom region's first stack, not panels: they are not saved in the layout, can't be dragged to another region, and close through the same unsaved-changes question as before. A region with no panel disappears, with its splitter, until a panel is moved or opened into it (while a tab is dragged, an empty region shows a drop strip).
- **Moving and closing.** Drag a tab, or a panel's header, onto another stack's tab bar (before that tab) or body (at the end), or onto the strip of an empty region. For the keyboard and the mouse alike, a tab's or a header's context menu (or the Menu key or Shift+F10 on a focused tab) has **Move to** each other region (into its first stack) and **Close**. The tab's x button and the Delete key close it too. A panel in a hidden tab keeps its state (it stays mounted), except the viewport and the console, which are unmounted while another tab of their stack is shown: **the viewport's renderer is disposed (its frame requests stop) and a new one starts when it is shown again**, rather than a paused one being kept. The camera is in `ViewportController`, so it survives that.
- **Window menu** (the toolbar, after Edit). Every panel, shown ones checked: choosing a shown panel that can be closed closes it, choosing a closed one opens it where it starts (in the right region, in its place between the others), choosing one that can't be closed switches to its tab. Then **Reset layout**, **Save layout as the default for new projects** and, once one is saved, **Forget the saved default layout**. The last item, **Keyboard shortcuts**, shows the list of shortcuts (see "Preferences and keyboard shortcuts").
- **Keyboard.** The bars are `role="tablist"` with `role="tab"` tabs and `role="tabpanel"` panels (`aria-selected`, `aria-controls`, `aria-labelledby`), one tab in the tab order (the shown one: roving `tabindex`). Left and Right arrows switch (and wrap), Home and End go to the first and last, Enter and Space switch, Delete closes, and the focus is visible. The context menu (`ContextMenu` in `ui.tsx`) now takes the arrow keys, Home, End and Enter, and one opened from the keyboard takes the focus and gives it back on Escape; a menu opened with the mouse closes on any other key, as it did.
- **The model** (`layout-model.ts`, pure functions that return the new layout, or the same object when nothing changes). `{version, regions: {left|center|bottom|right: {groups: [{id, tabs, active}], size}}, closed: [panel ids]}`: each stack has an `id` ("s1", "s2", ...) that names it for as long as it exists, so the view keeps a stack's panels mounted when closing or moving a tab changes the stacks around it (the view keys its stacks by it, not by position); a layout saved before stacks had ids (release F1) gets ids when it is read, in reading order, so reading it again gives the same ones, and a missing, malformed or repeated id is replaced the same way. `size` is the width (left, right) or height (bottom) in CSS pixels within the limits the splitters always had (150-500, 200-600, 80-700), raised by a panel's `minSize`. `closed` is what tells a panel the user closed from one a newer editor added: a panel that is in neither is put where it starts when a layout is read. `parseLayout` validates and migrates and never throws: unknown panels and repeats are dropped, empty stacks removed, a shown tab that isn't a tab becomes the first, sizes are clamped, a viewport that was somehow closed is shown again, and a value that isn't a layout of a known version (corrupt, or saved by a newer editor) gives null, which means the default. `Migrations` holds the steps from an older version (none yet: version 1 is the first).
- **Where it is kept** (`layout-storage.ts`, `layout-controller.ts`). In the editor's preferences (see "Preferences and keyboard shortcuts"): the project-scope pref `layout` for the open project (the id comes from `GetProjectInfo`, `project.projectId`, so a remote host's project has its own layout on this machine) and the user-scope pref `layout.default` for the default new projects start from. The stored value is the layout model's own JSON, unchanged. **Layouts saved by release F1** are kept under `n2.layout.project.<projectId>` and `n2.layout.user`; those entries are still read when the preference has no value, are never written, and are removed by **Reset layout** and **Forget the saved default layout** (or the old layout would come back). The fallback is dropped one release after this one. Every access is in try/catch and a failure only means the layout isn't remembered across runs: the editor still works for the session (the preferences keep what was set until the page closes). A change is saved 400 ms after the last one (a splitter drag changes the size on every pointer move), and what is waiting is saved when the editor closes or another project opens. Opening or closing a text file changes nothing that is saved. Until the host has answered `GetProjectInfo` the layout is the user default (or the built-in one), and an arrangement made before the id arrives becomes the project's. **Reset layout** forgets the project's layout and shows the user default, or the built-in layout when none was saved. Only panel ids, stack ids, tab order, the shown tab and sizes are stored: no paths, file names, tokens or text.
- **Not verified in a real Electron window yet:** how a tab drag feels (jsdom has no `DataTransfer`, so the drops are tested with a hand-made one), the splitters' limits at small window sizes, and the look of a stacked tab bar over a panel's own header. The default arrangement's boxes were compared with the old markup's in headless Chrome with stand-in panels (identical to within the 1 px border that moved from the panel to its stack); the real panels were not.

## MCP (n2-mcp)

`n2-mcp` is a stdio [MCP](https://modelcontextprotocol.io) server that lets an AI agent (Claude Code, Claude Desktop, any MCP client) **inspect and change** an N2Engine project through an editor host: the scene hierarchy, entities and their components, component schemas, assets, text assets, the console and screenshots (read tools), and entity edits, scene and text asset writes, project settings, undo and agent sessions (write tools, below), and, with `--launch`, playtesting the scene in a game of its own (play tools); the same reads are resources a client can subscribe to, and a few prompts arrange the tools into tasks (MCP3, below).

It is a separate Node program in `mcp/` (single-file bundle `dist/n2-mcp.mjs`, plain Node 22 or later, no Electron). It reuses this repo's protocol client (`src/protocol/`) and host launcher (`src/main/host-launcher.ts`), and talks to the host as an ordinary editor protocol client with its **own token**, so the host's roles, read-only mode, single-session rule and audit lines apply to the agent exactly as to a person. The design is the engine's MCP proposal (decisions M1-M12).

```
npm run build:mcp   # dist/n2-mcp.mjs (npm run build also does it)
npm run mcp:golden  # regenerate mcp/tool-schemas.golden.json after a deliberate change to a tool
```

### Backends

```
node dist/n2-mcp.mjs --launch <projectPath> [--host-path <N2EditorHost>] [--renderer opengl|software]
node dist/n2-mcp.mjs --connect <host:port> --fingerprint <sha256> (--token-env <VAR> | --token-file <path>) [--user <name>]
```

- **`--launch`** starts a host of the bridge's own for the project (`N2EditorHost --project <dir> --port 0 --tokens-file <temp file> --exit-on-stdin-eof`, found with `--host-path` or the `N2ENGINE_HOST` variable the editor also uses). Its one user, `n2-mcp`, has the **editor** role and a fresh random 256-bit token: the bridge writes only the token's SHA-256 to a 0600 file in a new temp folder, never puts the token in the arguments or the child's environment, and removes the file and ends the host when it exits (stdio closed, a signal, or the process ending; the host also ends by itself when the bridge's pipe to it closes). It needs a host built with TLS support (the tokens file uses SHA-256). The host is started on the first tool call, not at startup.
- **`--connect`** reaches a running host over **TLS with a pinned certificate fingerprint**. `--fingerprint` is required (64 hex digits, colons allowed): there is no trust on first use, because nobody is at the prompt. Get it from the host's ready line (`N2EditorHost ready port=... tls=1 fingerprint=...`) or from the editor's remote connection dialog. Plaintext is refused. The token is read from the environment variable named by `--token-env` (and removed from the environment) or from `--token-file` (on POSIX refused when group or others can read it). **A token is never accepted as a command line argument**, and is never logged.
- Other options: `--user <name>` (the token's user in the host's tokens file), `--allow-admin`, the write policy flags (below), `--busy-wait <ms>` (default 3000, at most 10000), `--call-timeout <ms>` (default 60000), `--ready-timeout <ms>`.
- The bridge says Hello with `errorCodes`, so the host's refusals arrive with codes. The host's role decides what works; the bridge adds nothing to it.

A session with the host is opened on the first tool call, or on the first `tools/list` (the bridge asks the host who the token is, so that the write tools are listed or hidden correctly; with `--read-only` a client that only lists tools never holds the host's single session), is checked once, and is used by one tool call at a time. When the host is busy (another editor or agent holds it) the bridge waits `--busy-wait` and tries **once** more, then answers with a `busy` error; it never retries in a loop. A dropped or idle-closed session is reopened by the next call. A call the host doesn't answer within `--call-timeout` drops the session and fails with `timeout`.

### Tools

The eleven read tools are `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`, have `additionalProperties: false` input schemas and an `outputSchema`, and answer with structured content plus a text block. The exact list, descriptions and schemas are pinned in `mcp/tool-schemas.golden.json` (a test fails when they change without it).

| Tool | What it does |
|---|---|
| `n2_status` | Where am I: protocol and engine versions, the role, whether the host is read-only, the project, the open scene (and whether it has unsaved changes), play state, engine health, undo history size. Call first. |
| `n2_get_project_info` | Name, id, engine version, startup scene, scenes and settings. No host paths. |
| `n2_get_hierarchy` | The scene's entities, depth-first, 200 per page (`limit` up to 2000, `cursor`, `rootId`, `maxDepth`). |
| `n2_get_entity` | One entity: header, local and world transform (position, quaternion, scale), up to 50 children, components with their saved values (64 KB budget, `componentTypes` filter). |
| `n2_get_component_types` | The component types the host can create (`filter` by name). |
| `n2_describe_component` | One type's fields as JSON Schema 2020-12 (types, ranges, enums, references as UUID strings, read-only, defaults); a LuaComponent's script fields by `entityId` and `componentId`. |
| `n2_list_assets` | Folders and assets (`folder`, `recursive`, `type`, `cursor`, `limit`). |
| `n2_get_asset_info` | One asset by path or UUID: type, size, sub-assets, import settings. |
| `n2_read_text_asset` | A text file's text, at most 100 KB per call, with `offset` and `length` in bytes (on character boundaries), a truncation note and `nextCursor`. |
| `n2_get_console` | The host's log lines: the latest `limit`, or what is new since `cursor`; `level`, `contains`. |
| `n2_screenshot` | A PNG image: `view` `editor` (default; the editor camera, `RenderFrameIfChanged`) or `game` (`RenderFrame`, the main camera); 768x432 by default, long side at most 1568 px (larger requests are reduced, keeping proportions). It leaves the host's viewport at the picture's size. |

Every result has the same shape: `{source, untrusted, truncated, nextCursor?, notes?, data}`, and its text block is a one-line summary followed by the same JSON in an `<n2-data source="..." untrusted>` envelope.

### Write tools

Write tools are **listed only when the host lets this token change the project**: an `editor` role (or an `admin` the operator allowed with `--allow-admin`) on a host that is not `--read-only`, and not hidden by the flags below. A viewer token or a read-only host gets the 11 read tools only. The bridge asks the host once, on the first `tools/list` (or on a write call that comes first), and sends `tools/list_changed` if the answer changes later. A host that can't be reached at that moment lists the read tools only (fail closed). The host still enforces its role gate on every command; hiding the tools is courtesy, not security.

**One undo step per call.** Every edit tool runs its host commands inside one edit group labelled `AI: <tool> #<n>` (it shows in the editor's Edit menu), opened and closed inside the call and never held between calls. If a command fails, the group is closed and, when the host already made a step for it, that step is undone at once, so a failed call leaves nothing; the error says whether nothing was applied, the step was undone, or (the connection dropped) the outcome is unknown. Every answer carries the host's edit result: `label`, `revision`, `savedRevision`, `dirty`, `canUndo`, `canRedo`, and the session's write counter.

| Tool | What it does |
|---|---|
| `n2_create_entity` | An entity with name, parent and place, a preset (Empty, Cube, Sphere, Quad, Light, DirectionalLight, PointLight, SpotLight), local transform (position, quaternion rotation, scale), tag, layer, active, and components with initial field values: one step. |
| `n2_destroy_entity` | Deletes an entity and its children (undoable). |
| `n2_set_transform` | Part or all of the local transform; the parts left out keep their values. |
| `n2_set_parent` | Reparents (`parentId` null for the root), `siblingIndex`, `keepWorldTransform`. |
| `n2_set_properties` | Name (this is the rename), active, tag, layer. |
| `n2_add_component`, `n2_remove_component`, `n2_set_component_fields` | Components by type name from `n2_get_component_types`; field values keyed by name as `n2_describe_component` shapes them. Type and field names are checked in the bridge first (with "did you mean"); the host checks the values all or nothing and its clamped values are echoed. |
| `n2_duplicate_entity` | A copy with children and components. |
| `n2_apply_batch` | Up to 500 ops of the kinds above as **one step, all or nothing**. Ops can use `$<n>.entityId` / `$<n>.componentId` of an earlier op. The first failure closes the group and undoes it, and the error says `Op <n> (<kind>) failed` and that nothing was applied. A bad reference or an unknown component is refused before the host is touched. |
| `n2_undo`, `n2_redo` | Move the agent's **own** steps only (the labels must match the host's history exactly): if a person edited after the agent, or the history was cleared, they refuse with `session_conflict` and change nothing. |
| `n2_create_scene`, `n2_open_scene`, `n2_save_scene` | `NewScene`, `OpenScene`, `SaveSceneToFile`. Opening or creating clears the host's undo history. |
| `n2_write_text_asset`, `n2_create_script` | Create or overwrite a text file under `assets/` (at most 100 KB, 200 files per session); `n2_create_script` makes a Lua script from the template (never overwrites). Not undoable by the host: an overwrite keeps the previous text as a **backup** in the session. |
| `n2_set_project_settings` | A JSON merge patch of the project settings (16 KB, 8 levels deep). A patch naming the `determinism` block is refused unless the bridge runs with an admin token the operator allowed. |
| `n2_begin_session`, `n2_session_summary`, `n2_end_session`, `n2_session_revert` | Agent sessions, below. |

Every tool except `n2_begin_session` takes an optional `sessionId`; without one the call is journaled in the implicit session. Annotations: `readOnlyHint: false` (true for `n2_session_summary`) and `openWorldHint: false`; `destructiveHint: true` for destroy, remove component, batch, undo, the scene, text asset and project settings tools, and session end and revert; `idempotentHint: true` for the `set_*` tools, save and write. They are hints only: clients treat them as untrusted, and the safety below does not rely on them.

#### Agent sessions

`n2_begin_session({label})` answers an opaque `sessionId` (a UUID) that later calls pass. Sessions expire after 24 hours without use or when the bridge exits (16 at once). A session holds:

- a **journal**: per write, the tool, a scrubbed one-line summary, the undo step's label, the entity ids touched, the file written with its hash, and how an irreversible operation was confirmed. It never holds a file's text;
- the labels of its own steps that are still done or undone;
- the write counter;
- the **backups** of text files it overwrote: a 0600 file in a private temp folder (memory if that fails), deleted at exit unless `--keep-journal`.

`n2_session_summary` says what changed (steps, entities created, destroyed and modified, files, whether the scene was saved after the last edit, settings, whether the history was cleared, whether the scene has unsaved changes right now) and shows the newest journal entries. `n2_end_session` answers the final summary and forgets the session.

`n2_session_revert` undoes the session's steps in reverse, then restores the files it overwrote from the backups. It works **only while the host's newest undo steps are exactly the session's own, in order** (otherwise it refuses and changes nothing). It restores a file only if it still holds what the agent wrote, and leaves files the agent created in place (the host cannot delete files), listing them. Restoring files is irreversible and gated like the operations below; `restoreFiles: false` reverts the steps only.

#### Irreversible operations: the person or the operator, never the model

Saving the scene, opening or creating a scene **over unsaved changes**, project settings, **overwriting** an existing text file, and a revert that restores files cannot be undone by the editor. Each such call first looks at the host (is the scene dirty? does the file exist?) and, when it really is irreversible:

1. with `--allow-irreversible` it runs (the operator's consent; the journal says `operator`);
2. else if the client declared **elicitation** (form mode; both `{form:{}}` and the older `{}`), the bridge asks the person a yes/no question that names the exact operation, and runs it only on an accepted yes (`elicited` in the journal). A decline, a cancel, or a yes that says false is `confirmation_declined`. The answer is tied to the operation by a key made from the tool and the question's text, so an answer never covers a different operation;
3. else it is refused with `irreversible_refused`, and the host is never asked.

**No argument a model sends is consent**: there is no `confirm` flag, every input schema refuses unknown keys, and the answer comes from the client's own channel (`inputResponses` are lifted out of the request before the tool sees its arguments). Reversible forms need no question (a new file, a clean scene, edits). Elicitation is written once with the SDK's `inputRequired()`. On 2026-07-28 it is the multi-round-trip pattern (an `input_required` result, then a retry with `inputResponses`); on 2025-11-25 the SDK's shim sends a real `elicitation/create` to the client and re-enters the call.

#### Write policy flags

| Flag | Effect |
|---|---|
| `--read-only` | No write tool is listed or callable, whatever the host allows (and listing never connects). |
| `--allow-irreversible` | The operator's consent for the irreversible operations above, for clients that can't ask. |
| `--max-writes <n>` | Host write commands per agent session (default 2000). |
| `--write-tools a,b` | List only these write tools. |
| `--disable-tools a,b` | Never list these tools, read or write. |
| `--keep-journal` | Keep the backups folder at exit. |

```
node dist/n2-mcp.mjs --launch . --renderer software --max-writes 500 --write-tools n2_create_entity,n2_set_transform,n2_undo
node dist/n2-mcp.mjs --connect editor.example.net:9999 --fingerprint <sha256> --token-env N2_AGENT_TOKEN --read-only
```

### Play tools, resources and prompts (MCP3)

**Play tools (`--launch` only).** A bridge that launched its own host can playtest the open scene. The game is a second `N2EditorHost` that the bridge starts through the editor's own play code (`src/main/play-session.ts`): the edit host writes a snapshot of the open scene as it is in memory (unsaved edits included, nothing saved, no revision moves), the bridge starts `N2EditorHost --play <snapshot>` with the same project and renderer and a fresh token in the child's environment only, and connects to it. Nothing done in the game changes the scene or the project. A `--connect` bridge has **no play tools at all**: they are not registered, not listed and not callable, whatever it is given (design M9: remote play stays disabled). A play call the bridge times out (`--call-timeout`) is aborted like a cancelled one (it stops between steps and releases its input), and the next call waits for it to end. The play tools are write-class: they are listed with the write tools (an editor token on a host that is not read-only, not hidden by `--write-tools` / `--disable-tools`), so a viewer may not play.

| Tool | What it does |
|---|---|
| `n2_play_start` | Starts the game from the open scene and answers its state (`playing`, frame, time, the game's number). A second call answers the running game. A game that can't start is `play_failed` with its own words, scrubbed. |
| `n2_play_stop` | Ends the game (Shutdown, then a kill after a grace period). No error when none runs. |
| `n2_play_control` | `pause`, `resume`, or `step` 1 to 600 frames of a **paused** game (each one fixed timestep, so a test repeats exactly). A step runs as `Step` commands of 100 frames with a progress notification and a cancellation check between them. |
| `n2_play_input` | Up to 256 input events (`key`, `mouseButton`, `pointer`, `scroll`, `releaseAll`), applied all or none; key names are checked by the host. |
| `n2_play_observe` | The game's state, its log lines since the previous observe (scrubbed like the console, audit lines and `peer=` dropped), up to 8 live entities by id (transforms and component values, 64 KB) and, with `screenshot: true`, a PNG of the game's main camera. |
| `n2_play_script` | A playtest in one call: up to 50 ops `{input}`, `{step}` (3000 frames in all), `{screenshot}` (at most 4, long side 1024 px, 6 MB together) and `{expectLog: {contains, level?, absent?}}`. The game is paused first and left paused, so frames advance only by step ops. One progress notification per op (numbers and the op's kind, never project text); cancellation is checked between ops and between step chunks. A failed `expectLog` stops the script unless `continueOnFailure`. A script that ends early (cancelled, or an error) sends `releaseAll`, so no key or button is left held. |

Budgets per agent session: every `Step` chunk, `SetPaused`, `SendInput` and the snapshot count against `--max-writes`; 20,000 stepped frames and 50 game pictures. New error codes: `play_not_running` (no game, or it ended: `n2_play_observe` shows why), `play_failed`, `cancelled`. The game's host token is the play child's own (as in the editor); it is registered as a secret and redacted if a game ever echoes it, and the snapshot's absolute path is never returned.

**Resources.** The same reads, addressable by URI, for clients that show resources. Each read runs the matching read tool, so its text is that tool's summary and data in the `<n2-data ... untrusted>` envelope (`mimeType: text/plain`, `_meta` `n2/untrusted`, `n2/source`), scrubbed and size-limited the same way; reads count against the 120 calls a minute. A read the host refuses is a JSON-RPC error carrying the bridge's scrubbed error text. `--disable-tools` turns a resource off with its tool: it is then not listed, readable or watchable (`n2://scene` and `n2://history` go with `n2_status`).

| URI | What | Announced when |
|---|---|---|
| `n2://project` | `n2_get_project_info` | `projectChanged` |
| `n2://scene` | the open scene's path, revision and dirty flag | `sceneChanged` |
| `n2://scene/hierarchy` | the first page of `n2_get_hierarchy` | `sceneChanged` |
| `n2://entity/{uuid}` | `n2_get_entity` | a `sceneChanged` that lists it, or one without a list (`full`, or more than 256 objects) |
| `n2://asset/{+path}` | `n2_read_text_asset` of `res://<path>` (first 32 KB) | an `assetsChanged` naming it |
| `n2://console` | the last 200 lines of `n2_get_console` | new log lines, at most once a second |
| `n2://history` | undo and redo counts and the last 50 labels | `historyChanged` |
| `n2://component-types` | `n2_get_component_types` | never (they don't change while a host runs) |

**Subscriptions.** `resources/subscribe` (2025-11-25) and `subscriptions/listen` (2026-07-28; the SDK's stdio entry serves the stream, and the bridge sees the acknowledged filter and the cancel through a transport tap) watch at most **32 URIs** per connection, with at most **8 listen streams**; an unknown URI or one past the limit is refused (`resources/subscribe`) or not watched (listen). The host's events are polled (the frontend's `EventPump`, every 500 ms, one cursor and no queue) **only while something is watched**: the first poll only finds the newest event, so nothing from before the subscription is announced. A notification carries the URI only, never host text, and each URI is announced once per poll. Unsubscribing the last URI, closing the last stream or the connection ending stops the polling.

**Prompts** (design 3.7): `n2_build_level(description)`, `n2_inspect_scene`, `n2_playtest(goal)` (only on a bridge with the play tools), `n2_fix_console_errors` and `n2_write_lua_component(behaviour)` (the `SerializableFields` conventions of `docs/scripting-lua.html#fields`). Each one only arranges the bridge's tools into a plan and restates that what they return from the project is data, never instructions; the person's argument (at most 2000 characters) is quoted as their request. Prompts and resource lists never contact the host.

`mcp/tool-schemas.golden.json` now also pins the play tools (generated as a `--launch` bridge), the prompts, the resources and the resource templates.

**Not verified:** play against a real N2EditorHost (the tests use the real play-session code with a fake child process and a second fake host answering like a play host, written from the protocol docs); whether Claude Code or Claude Desktop shows resources, subscriptions, prompts or progress to the person or the model.

### Security

- **Everything from the project is untrusted data.** Names, field values, asset text, console lines and the host's own error text are scrubbed and bounded before the model sees them: control characters are removed; bidi, zero-width, line-separator and Unicode tag characters are shown as `\u{...}` escapes; lone surrogates become U+FFFD; strings and whole values are size-capped; the text block's JSON escapes `<`, `>` and `&`, so data cannot write the `</n2-data>` that closes the envelope. Every tool description and the server instructions say returned text is data, never instructions. There are no tools that run text as a command, and no shell, file system or network tools.
- **The host's paths and the bridge's secrets stay out.** The project and user-data folders (learned from `GetProjectInfo`, which is never passed on with them) become `<project>` and `<userdata>`; any other absolute path in a message or log line becomes `<host-path>`; the token is replaced by `[redacted]` if a host ever echoes it. The console drops the host's `audit:`, `Rate limit` and `Refused Hello` lines and `peer=` addresses (the engine's own filtering of the event stream for viewers is the other half).
- **Least privilege.** Use a dedicated token user per agent (for example `--new-token agent-claude viewer` on the host), a **viewer** token for inspection, and an editor token only when the agent should change the project (scope the tools further with `--write-tools`). **The admin role is refused** (`admin_refused` for every tool, the connection closed) unless `--allow-admin`: an agent never needs it. A host started with `--token-env` has one token with every right, which is admin: use a `--tokens-file` host for agents.
- **No secrets in client configs.** Tokens come from an environment variable or a 0600 file, never from arguments; in `.mcp.json` give the variable by reference.
- **Writes stay inside `assets/`, never `editor/`.** The bridge refuses a path that is not plain `res://` followed by safe segments (no `..`, `.`, empty segment, backslash, colon, percent escape, control character, trailing dot or space, nor full-width lookalikes, which NFKC would change), whose first segment is `editor` (or `assets/editor`), or that ends in `.meta`. It does so before the host is asked anything, not even to read. The host refuses again (extension allow list, symlinks, the open scene's own file). Editor extensions run with capabilities of their own, so an agent must never be able to plant one.
- **No shell, no file system, no network.** The bridge has no tool that runs text or touches the agent machine's files. Lua is written only as an asset.
- A hostile host can only return data (scrubbed and bounded as above). A screenshot can show text rendered by the project: that is data too.

### Errors

A failed call is `isError: true` with `_meta["n2/errorCode"]` and a text of the code, a fixed message, one sentence of advice and, for the host's own refusals, its words quoted as untrusted data. Raw exception text never reaches the model (it goes, scrubbed, to the bridge's stderr). The codes: `invalid_argument`, `rate_limited`, `read_only`, `forbidden`, `busy`, `auth_failed`, `fingerprint_mismatch`, `incompatible_protocol`, `connection_lost`, `host_unavailable`, `admin_refused`, `timeout`, `extensions_disabled`, `extension_failed`, `extension_faulted`, `host_error`, `result_too_large`, `internal`. Arguments that fail the schema are `isError` results too (the SDK's validation message).

### Spec revisions

The bridge uses `@modelcontextprotocol/server` **2.3.1** (pinned, bundled into `dist/n2-mcp.mjs`, with `zod` 4.6.7 for the schemas). It serves MCP over stdio with the SDK's `serveStdio`, which decides per connection how the client opens it: **2026-07-28** (the current revision: `server/discover`, the protocol version in every request's `_meta`) or the handshake-based **2025-11-25** (`initialize`) and the older ones the SDK still accepts. Both are tested against the SDK's own client (`mcp/test/conformance.test.ts`). A client on 2026-07-28 with version negotiation `auto` first starts a short-lived probe copy of the bridge for `server/discover`; because the host is only reached on the first tool call, that copy never starts a host or takes the host's session. The tool annotation names (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) are those of the SDK's tool schema, which serves both revisions.

### Spec findings for the write tools

Checked on 2026-10-20 against modelcontextprotocol.io and the pinned SDK 2.3.1.

- **Annotations:** a tool's `annotations` has `title`, `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint` (the SDK's `ToolAnnotationsSchema`, used for both revisions). The 2026-07-28 tools page only says that annotations are untrusted hints unless the server is trusted, without listing the names.
- **Elicitation, 2025-11-25:** the client declares `elicitation: {form:{}, url:{}}` (an empty `{}` means form only). The server sends `elicitation/create` with `mode: "form"` (optional), `message` and a flat `requestedSchema`. The answer's `action` is `accept` (with `content`), `decline` or `cancel`.
- **Elicitation, 2026-07-28:** the server answers `tools/call` with `resultType: "input_required"` and `inputRequests` (embedded `elicitation/create` objects keyed by the server); the client retries with a new request id and `inputResponses`. Client capabilities travel in every request's `_meta` (`io.modelcontextprotocol/clientCapabilities`). The bridge reads them from `ctx.mcpReq.envelope` first, then from the `initialize` capabilities.
- **A caveat:** the 2026-07-28 page says the tool list MUST NOT vary per connection or as a side effect of other requests, but MAY vary by the authorization presented. On stdio the token is process-wide configuration, so the list is constant for a given token. It can change once (read tools only until the host has been reached), which the bridge announces with `tools/list_changed`.

## Preferences and keyboard shortcuts

Roadmap phase F2 (issue #6's UI roadmap, decisions U2 to U4). The editor keeps its settings in one preferences store and its shortcuts in one keymap, so a later feature adds a key or an action instead of a `localStorage` call or a `keydown` listener.

**Preferences** (`src/renderer/prefs.ts`, framework-free).

- **Keys.** `definePref({key, scope, default, validate, legacyKey?})` defines a typed key (dotted words, `"layout.default"`); `v.boolean`, `v.string`, `v.number(min, max)`, `v.oneOf`, `v.arrayOf` and `v.object` are the validators. Two scopes: `user` (global to this machine) and `project` (the project's id, as the layout has it; an id that isn't made of letters, digits and dashes gives a scope that remembers nothing). `appPrefs().user.get(key)`, `.set(key, value)`, `.remove(key)` and `.subscribe(key, listener)`; `appPrefs().project(id)` has the same for project keys. A value that fails its validator is refused by `set` (it returns false). Keys today: `layout` (project), `layout.default` (user), `keymap.overrides` (user), `hierarchy.filter` (project: the hierarchy search text and mode) and `console.filter` (project: the console's levels, hidden sources, text, case and regex toggles, and collapse).
- **Storage.** One `localStorage` entry per key: `n2.prefs.user.<key>` or `n2.prefs.project.<projectId>.<key>`, holding `{"version": 1, "value": ...}`. Every access is in try/catch (storage can be missing, full or blocked: nothing throws, and a value still applies until the page closes). An entry that is corrupt, of the wrong type or fails its validator is not used (the default applies) and is removed; an entry of a newer version (written by a newer editor) is not used and is never overwritten. A key can name a `legacyKey`, an older release's entry, which is read when the new entry is absent and removed together with it (the layout uses this: see "The layout and the Window menu").
- **Writes** are debounced (300 ms after the last change) and written at once on `flush()`, with `{immediate: true}`, and when the window is hidden or closed (`pagehide`, `beforeunload`). Values are cached: a change made by another window is seen the next time the editor starts.
- **No secrets.** A key whose name looks like a secret (token, secret, password, passphrase, credential, api key, private key, auth, bearer, session id) cannot be defined, so there is no way to store one. Connection tokens stay in the main process and the host's environment; nothing in the preferences is sent anywhere.

**The keymap** (`src/renderer/keymap.ts`, framework-free; the panels' side is `keymap-hooks.ts`).

- **Actions.** A registry of named actions, each with a title, a scope, default chords and optionally `allowInText`. Only actions that exist today are in it (the names the roadmap reserves for the gizmo's space and pivot toggles and camera bookmarks are comments in `keymap.ts`, not code). A panel registers what runs an action with `useKeymapActions({ "hierarchy.rename": (e) => ... }, ref)` for as long as it is mounted (`ref`: only for key presses inside that element); a handler that returns `false` did not take the key.
- **Chords** are written `Mod+Shift+Z`: modifiers `Mod` (Ctrl or Cmd, whichever the press has, as undo and save always accepted both), `Ctrl`, `Cmd`, `Alt`, `Shift`, then one key, either a `KeyboardEvent.key` (`ArrowDown`, `Delete`, `F2`, `z`) or a `code` (`KeyF`, which is that physical key on any layout: a code chord for a letter, digit, punctuation or numpad key matches only the key at that place, never a key that merely types the same letter, so a layout whose F key types another letter still frames and a key that types an f elsewhere does not; named keys such as `Escape` and `F2` are a code and a key alike). Modifiers are matched exactly. `Mod` is shown as Cmd on macOS and Ctrl elsewhere.
- **The dispatcher** is one `keydown` listener on the document, installed by the editor (installing again replaces it, so there is never more than one). A key press that something already took (`defaultPrevented`) or that is composing text is left alone. Otherwise the actions whose chord it is are candidates, in this order: those of the **scope of the focus** (the nearest ancestor with `data-keymap-scope`: the viewport container, the hierarchy list, the assets panel, the console panel, a text editor), then the global ones; an action of another scope never runs. A dialog open (`modalOpen()`, the shortcuts list included) stops everything. While a text field has the focus (`isTextEntry`) only actions with `allowInText` run, so nothing fires while typing: the saves do (Ctrl+S saves from a field, as it did), undo and redo don't (the field's own undo is meant). A key an action takes has its default prevented.
- **The viewport's fly keys** (W A S D Q E and the arrows, held while the right button is down) keep their priority exactly: the view's own listener takes them first and prevents the default, and the dispatcher leaves a prevented key alone, so a fly key is never also a shortcut, whatever is bound to it (`viewport-keys.ts`). W, E and Q are tool keys too (`gizmo.*`, below): they fly only while the right button is held and choose a tool otherwise. The keys of a live game view are the game's, as before. Keys that belong to a widget rather than the editor (a tab bar's arrows, a menu's, a dialog's Escape and Enter, a field's Enter and Escape) stay with the widget.
- **Default chords.**

| Action | Chord | Where | What it does |
|---|---|---|---|
| `file.save` | Ctrl/Cmd+S | everywhere, text fields too | commits the inspector, saves the scene (nothing without a scene, or while busy) |
| `text.save` | Ctrl/Cmd+S | a text editor | writes that file (not the scene) |
| `assets.applySettings` | Ctrl/Cmd+S | the import settings field | applies the edited settings (anywhere else in the assets panel Ctrl+S saves the scene) |
| `edit.undo`, `edit.redo` | Ctrl/Cmd+Z; Ctrl/Cmd+Shift+Z or Ctrl/Cmd+Y | everywhere, not in a text field | the host's undo and redo |
| `hierarchy.rename`, `.delete`, `.duplicate` | F2; Del; Ctrl/Cmd+D | the hierarchy list | nothing while read-only; Del and Ctrl+D act once for a held key |
| `hierarchy.next`, `.previous`, `.extendNext`, `.extendPrevious` | Down; Up; Shift+Down; Shift+Up | the hierarchy list | move the selection, or extend it |
| `hierarchy.search` | Ctrl/Cmd+F | the hierarchy list | focuses the search box |
| `hierarchy.expand`, `.collapse` | Right; Left | the hierarchy list | open or close the primary object |
| `viewport.frame`, `viewport.cancel` | F; Esc | the viewport | frame the selection; cancel a gizmo drag in progress |
| `gizmo.translate`, `.rotate`, `.scale`, `.none` | W; E; R; Q | the viewport | choose the gizmo's tool: move, rotate, scale, select only (not during a drag, and not in a game; W, E and Q fly while the right button is held) |

- **Compared with the per-component handlers they replace**, the default chords do the same in the same places. What differs: modifiers are matched exactly (Shift+F no longer frames; Ctrl+Down no longer steps; Shift+Delete no longer deletes, where those keys used to ignore a modifier they didn't use), and a dialog open now stops the hierarchy's and the viewport's keys too, not only Ctrl+S and undo.
- **Rebinding** is stored but has no UI yet: `keymap.bind(id, ["Mod+Shift+S"])` replaces an action's chords (an empty list unbinds it) and writes the user pref `keymap.overrides` (`{actionId: [chords]}`); `keymap.reset(id)` and `resetAll()` undo it. `bind` is all or nothing and reports a chord that doesn't parse, an action that doesn't exist, more than 8 chords (the most the stored overrides allow: a longer list would be dropped when read back), or a chord another action **of the same scope** has (a scope's action shadowing a global one with the same chord is how `text.save` works, not a conflict). Stored overrides are validated when read: an unknown action or a bad chord is skipped and the rest kept. The hierarchy's menu shows the current chords; the Edit menu's labels still name the default ones.
- **Keyboard shortcuts** (Window menu): a read-only list of every action with its current chords, by scope, in a table (`role="dialog"`, `aria-modal`, a caption and row headers; the focus goes to Close, Escape or Close closes it and the focus goes back). Nothing in it can be changed.

## Architecture

| Where | What |
|---|---|
| `src/protocol/` | The protocol client, with no DOM or Electron dependencies: reading frames (`framing.ts`), one spec per command built from the generated codecs (`codec.ts`), `EngineClient`, the `EventPump` for `PollEvents`, and the generated ids, types and codecs (`protocol.generated.ts`) |
| `src/main/` | The Electron main process. It launches the project's editor host (`host-launcher.ts`, `project-session.ts`, `host-settings.ts`) and, for play mode, the game's second host (`play-session.ts`, `play-ipc.ts`), opens the SSH tunnel to a remote engine (`ssh-tunnel.ts`, `recent-remotes.ts`, `remote-ipc.ts`; see "Remote engine"), owns the `EngineClient`s (the TCP connection to the host) and the open project's files, keeps the recent projects, and answers the page's IPC calls |
| `mcp/` | The `n2-mcp` bridge (see MCP (n2-mcp) above): its own tsconfig, bundled to `dist/n2-mcp.mjs`; no Electron. It reuses `src/protocol/` and `src/main/host-launcher.ts` and nothing else of the app |
| `src/shared/api.ts` | The typed API between the page and the main process: `window.engine` (protocol commands and connection state), `window.host` (the host process: state, restart, stop, locate), `window.remote` (connect to a remote engine, recent remotes), `window.play` (the game: start, stop, pause, step, and the child's frames, audio, events and input) and `window.project` (dialogs, recent projects, the project's text files), the IPC channel names, and the command allowlist |
| `src/preload/` | Forwards `window.engine`, `window.host`, `window.remote`, `window.play` and `window.project` calls over IPC. Bundled, since a sandboxed preload can require only `electron` |
| `src/renderer/` | The page, in Preact with `@preact/signals`, bundled by esbuild into `dist/bundle/renderer.js`. `store.ts` (`EditorStore`) holds the editor's state as signals (the open project, recent projects, the host, the connection, what is busy or failed) and its actions; `console-store.ts` holds the console. Both take the page's API as a parameter, so they are tested in Node. The components (`.tsx`) are the welcome screen, the editor layout and its panels. The hierarchy panel's state and rules are `hierarchy-state.ts` and `hierarchy-tree.ts` (see "The hierarchy and scenes"); the inspector's are `inspector-state.ts`, `inspector-fields.ts` and `asset-lookup.ts` (see "The inspector"); undo, redo, edit groups and autosave recovery are `edit-controller.ts`, `edit-groups.ts`, `edit-actions.ts` and `autosave.ts` (see "Undo, redo, edit groups and autosave"); the assets panel and the text editor are `assets-state.ts`, `asset-tree.ts` and `asset-edit.ts` (see "The assets panel"); the inspector's selection and transform are in `scene-state.ts`. The audio player is here too. The preferences store and the keymap are `prefs.ts`, `keymap.ts`, `keymap-hooks.ts` and `global-actions.ts` (see "Preferences and keyboard shortcuts"); the viewport's keys are `viewport-keys.ts` |

The window runs with `sandbox: true` and `contextIsolation: true`: the page has no Node and no raw file system. It can only call the commands in the allowlist, with arguments of the declared types (`EngineCommandArgs`), on the host the main process launched. It has no file access of its own: the project's files are read and written through the host's asset commands, which check every path (inside `assets/`, no links out, valid names, text types only, 4 MiB) and refuse the open scene's file and, in a play session, every write. The main process checks the arguments of each command. IPC is answered only for the editor's own page in its window's main frame; the window can't navigate, redirect or open windows, and every permission request is denied.

**Framing.** Every message is `[type: uint8][payloadLength: uint32 LE][payload]`. `FrameReader` keeps received chunks in a list and copies only once a whole frame has arrived, so a multi-MB viewport frame costs one copy however many chunks it arrives in (a frame inside one chunk isn't copied at all). Responses are matched to requests in order; type ids `0xC0`-`0xFE` are reserved for server-pushed events and never consume a pending request. Decoded `bytes` fields (a frame's pixels) are views into the payload. IPC posts a view's whole underlying buffer, so before a result goes over IPC the main process copies a view that uses only a small part of its buffer (one inside a socket chunk holding other frames); a frame assembled from several chunks owns its buffer, all but the 8-byte header of which is the pixels, and is posted without a copy.

**Hello.** Each connection starts with `Hello` (protocol 1.2): `connect()` sends the client name, the protocol version and the host's access token, and resolves with the host's `ServerInfo` (protocol and engine versions, capabilities, whether a project is loaded), which the page gets in the connection state. Nothing else is sent until it succeeds, and the pre-`Hello` payload is kept under the host's 64 KiB limit. A refused `Hello` (a wrong token, another major protocol version) or no answer within 10 s (the host's 5 s Hello deadline, which starts only when it accepts the connection, plus a margin) fails the connect and closes the connection, and the editor kills that host. The token is the one the editor generated for that launch (see "The editor host process"); the main process never sends it to the page. Hosts speaking protocol 1.0.x (no `Hello`) aren't supported: the editor is pinned to an engine commit (`engine-ref.txt`) and expects its protocol.

## Protocol

`src/protocol/protocol.generated.ts` (ids, types and an encoder and decoder for every message) is generated from the engine's `editor-server/protocol/protocol.json` by the engine's own TypeScript generator, and `src/protocol/test-vectors.json` is the engine's golden vectors, copied. Neither is edited by hand. After the protocol changes, regenerate them (needs Python):

```
npm run sync-protocol                      # the engine checked out next to this repo (../N2Engine)
npm run sync-protocol -- <path to N2Engine> # or anywhere else (or set N2ENGINE_DIR)
```

This runs `editor-server/protocol/generators/generate_typescript.py --out src/protocol/protocol.generated.ts`, so nothing in the engine repo changes. `src/protocol/codec.ts` builds each command's spec from the generated codecs, so a new command gets one with no hand-written layout; add the `EngineClient` method, and add it to `EngineCommands` and `EngineCommandNames` in `src/shared/api.ts` if the page should be able to call it.

### Protocol 1.14.0: Lua editor extensions (`EngineCommands`/IPC and the UI)

Protocol 1.14.0 (engine E-X2, PR #189) adds the host's Lua editor extensions. The client side is in `src/protocol/extensions.ts` and `EngineClient`; the UI built on it is described under "Editor extensions":

- **Commands.** `listEditorExtensions()` (`ListEditorExtensions`, 0x80, a read), `getEditorUi()` (`GetEditorUi`, 0x81, a read) and `reloadEditorExtensions()` (`ReloadEditorExtensions`, 0x84, admin only). Each returns an `ExtensionsResult`: `ok` with a typed value, `unsupported`, or `error` with a kind and the host's message; none of them throws. The JSON answers are parsed defensively (unknown fields ignored, missing ones defaulted, an unknown state counts as failed and an unknown `minRole` as admin, a shape that is not an object is a `malformed` error). They are on the IPC API (`src/shared/api.ts`: `window.engine.listEditorExtensions` and the others), forwarded by name with their arguments checked in the main process like every command.
- **Capability.** `EngineClient.hasCapability("editorExtensions")` reads `ServerInfo.capabilities`. Against a host without it (any host before 1.14.0) the three helpers answer `unsupported` without sending anything, so such a host is unaffected. A host that has the capability but was not started with `--editor-extensions` answers `enabled: false` and nothing listed, which is not an error.
- **Error codes.** `extensionsDisabled`, `extensionFailed` and `extensionFaulted` become the kinds `disabled`, `failed` and `faulted`, distinct from `forbidden`, `readOnly` and `busy` (which is `other` here). The code is the contract, never the message. `extensionFailed` and `extensionFaulted` are reserved in 1.14.0: nothing answers them until the commands that run an extension come.
- **Event.** `extensionsChanged` (with `uiRevision`, 0 when missing) is parsed with the other state events; `EditorStore.extensionsUiRevision` and `extensionsChangeCount` carry it (the revision resets to null when the connection changes); the Tools menu and the Extensions section fetch again when the count changes.
- **Not covered.** `InvokeInspectorAction` (0x83) is reserved and inspector sections are always empty, so neither is modelled. `InvokeMenuItem` and the `extensionOutput` event came with 1.15.0 (below).

### Protocol 1.15.0: running a menu item (`EngineCommands`/IPC and the UI)

Protocol 1.15.0 (engine E-X3, PR #202) lets a client run an extension's menu item. The Tools menu, the form dialog, the trust prompt, the launcher flag and the Extensions section are described under "Editor extensions". The client side is in `src/protocol/extensions.ts`, `src/protocol/extension-output.ts` and `EngineClient`:

- **Command.** `invokeMenuItem(itemId, selection, params, uiRevision)` (`InvokeMenuItem`, 0x82, a Write command, edit-only) returns an `ExtensionsResult<InvokeResult>`: `ok` with `{ result: { message, select, warnings }, edit: { label, revision, savedRevision, canUndo, canRedo } }`, `unsupported`, or `error` with a kind. Parts the host leaves out come back empty, unknown fields are ignored and a result part that is not an object is a `malformed` error; nothing throws. `selection` must be at most 4096 object UUIDs and `params` a plain object, else the call is an `invalid` error and nothing is sent. The caller settles pending inspector edits and ends its own edit groups first, as before an undo. It is on the IPC API (`src/shared/api.ts`, `invokeMenuItem`).
- **Gate.** The command has no capability of its own (a 1.14 host lists `editorExtensions` too), so `invokeMenuItem` needs the capability and a host that speaks 1.15 or later (`supportsInvokeMenuItem`); against any other host it answers `unsupported` without sending anything.
- **Error codes.** `staleUiRevision` becomes the kind `staleUi` (fetch `getEditorUi()` again, nothing ran) and `editGroupOpen` the kind `editGroupOpen` (end the edit group first, nothing ran), each distinct from `forbidden`, `readOnly`, `busy` (`other`) and the `disabled`, `failed` (the host took the changes back) and `faulted` kinds, which `InvokeMenuItem` now answers.
- **Output.** The `extensionOutput` event (`extension`, `level`, `message`, `time`; Admin-only, so other roles get none) is kept by `EditorStore.extensionOutput`, an `ExtensionOutputLog`: a bounded ring of 500 lines (oldest dropped) with `lines` and `subscribe(listener)`, emptied when a connection is made. An unknown level counts as info and a line without a text message is dropped. Every string is untrusted text from project code: control characters are replaced and long text cut, but it is not escaped, so whatever shows it must render it as text, never as HTML. The host also logs each line as an Admin log line, so an older client's console shows it; this editor shows the event itself, as an Extension line (see "Editor extensions").

### Protocol 1.16.0: inspector sections (`EngineCommands`/IPC and the inspector)

Protocol 1.16.0 (engine E-X5, PR #209) lets an extension add a section under the components of a type and run its buttons on one component. This editor is at 1.16.0 (`engine-ref.txt`, `npm run sync-protocol`). The client side is in `src/protocol/extensions.ts` and `EngineClient`; the UI in `src/renderer/extension-inspector.ts` (pure rules), `extensions-state.ts` and `inspector-panel.tsx` (`ExtensionSections`):

- **Sections.** `getEditorUi()` now carries `inspectorSections` (parsed defensively: a section with no component type, a button with no id and a repeated button id are dropped, an unknown role is the stricter one, a field that cannot be shown is left out; a host before 1.16.0 sends none). Under each component whose type matches a section's `componentType` the inspector shows the section's label, its fields as read-only text (the component's value by field name, a dash when it has none) and its buttons. Several objects selected show no sections.
- **Command.** `invokeInspectorAction(componentId, actionId, params, uiRevision)` (`InvokeInspectorAction`, 0x83, a Write command, edit-only) answers like `invokeMenuItem`: the same `ExtensionsResult<InvokeResult>`, the same error kinds (`staleUi`, `editGroupOpen`, `failed`, `faulted`, `disabled`, `forbidden`, `readOnly`) and the same one undo step. It needs the capability and a host of 1.16 or later (`supportsInvokeInspectorAction`), else it answers `unsupported` without sending; arguments of the wrong shape (a `componentId` that is not a UUID) are an `invalid` error, also unsent. It never throws.
- **Buttons.** A button runs the same steps as a menu item (pending edits sent, edit groups ended, the form dialog when it declares params, the call, the result as the notice, console lines and a selection). It is hidden for a viewer (the section's fields stay), disabled with the reason for an `admin` button when the role is editor, a read-only host or play session, an open edit group, another run, a host before 1.16.0 or an extension that is not loaded, and a stale revision (`staleUiRevision`) says so and fetches the sections again. The sections are fetched again on `extensionsChanged`. Every string an extension supplies is a text node or an attribute, never HTML.
- **Tests.** `src/test/engine-client-inspector.test.ts` and `src/test/extension-inspector.test.ts` (Node: wrapper, errors, gate, parsing, rules, the run) and `src/test-dom/extension-inspector.test.tsx` (DOM: rendering, button flow, role gating, stale revision, text).
- **Not verified.** The look of a section in the live editor, and a button against a real 1.16 host.

## Inspector multi-edit (FE11)

With two or more objects selected, the inspector edits them together (`inspector-multi.ts`, `MultiInspectorState`; the panel is in `inspector-panel.tsx`). No protocol change: it is built on `GetEntity`, `SetEntityProperties`, `SetLocalTransform`, `SetComponentFields`, `AddComponent`, `RemoveComponent` and the edit groups (`BeginEditGroup`/`EndEditGroup`).

- **What is shown.** The header fields (active, tag, layer), the local transform per axis, and the component types that ALL the selected objects have, matched by type (the first component of each type on each object). A `LuaComponent` is shared only when all of them run the same script; its script fields are then edited together. Where the objects differ the box shows a dash (a checkbox is indeterminate). References, lists and JSON fields are edited one object at a time (the card says how many are left out).
- **One undo step.** An edit sends one request per object whose value differs (`SetComponentFields`, `SetEntityProperties` or `SetLocalTransform`), one at a time, inside ONE edit group named "Edit N objects", so one Undo takes the whole edit back. **Add Component** adds the type to every selected object and **Remove** (the card's x, asked once: "Remove Light from 3 objects?") removes the shared component from every one of them, each as one group too. A singleton type that any selected object already has is listed but disabled.
- **Failure.** The first refusal aborts the edit: nothing more is sent, and the group is ended in a `finally` like every edit group (never left open: the host refuses Undo and extension invokes while one is). What was applied before the refusal is one undo step. The panel says "The edit stopped at a refusal: K of N changes applied (Undo takes back what was applied), M not sent." with the object's name and the host's reason, and the objects are read again, so what is shown is what the host has. A denial (a read-only host, a viewer) is also reported once to the error banner.
- **The selection changes while an edit is on its way.** The edit finishes on the objects it was made on (and stops at a refusal as above), its group ends, and its outcome is not reported on the new selection, which is read and shown on its own.
- **Read-only.** A play session, a read-only host or a viewer role disables every box, Add Component and Remove; nothing is sent.
- **Tests.** Node: `src/test/inspector-multi.test.ts` (common fields, mixed values, fan-out in one group, abort on refusal, stale selection, Add/Remove for all, read-only). DOM: `src/test-dom/inspector-multi-edit.test.tsx` over a fake host that keeps an undo history where a group is one step (mixed display, one undo step, partial failure, a selection change while an edit is on its way, Add/Remove for all, read-only).

## Marquee selection in the viewport

A left drag that starts on empty space in the viewport (not on a gizmo handle) and moves past the click slop draws a selection rectangle; on release the objects under it are selected. A press that stays within the slop is still a click (pick), and a press on a gizmo handle is still a gizmo drag.

- **What it takes.** Each object of the hierarchy that is active in it is measured with `GetEntityBounds` (its world AABB, which the host makes the union of the object and everything under it). The box is projected the way the selection box is drawn: every edge is clipped against the near plane before the perspective divide, so a box wholly behind the camera is never taken and one the near plane cuts gives the rectangle of the part in front. By default an object is taken when that screen rectangle intersects the marquee; with **Alt** held during the drag (read at the release) only when it lies wholly inside, and a box the near plane cuts is never wholly inside. Alt at the press is still the orbit. Precision is AABB-level: a parent whose box encloses a child it touches is taken too.
- **Keys at the release.** No key replaces the selection (an empty marquee clears it, as a click on empty space does); **Shift** adds what it took (the primary object stays); **Ctrl** or **Cmd** removes it (and wins over Shift). **Escape** during the drag drops the rectangle and leaves the selection alone. The rows of what is selected are revealed in the hierarchy. The wheel does not zoom while a marquee is drawn.
- **Bounds cache.** The boxes are asked for when the marquee begins and kept per hierarchy revision, connection and scene change (any `sceneChanged` drops them), so repeated marquees over an unchanged scene ask the host once. More than 4096 objects are asked in chunks of 4096 (the host's cap per call). An answer that arrives after the connection changed, or after a later click or change of the selection, is not applied.
- **Code.** `src/renderer/viewport-marquee.ts` (projection and intersection maths, candidates, the selection rule, the cache and the gesture's event glue), `ViewportController` (the gesture: `pointerMove`/`pointerUp` take the marquee keys, `marqueeShape()` for the overlay, `cancel()`), the overlay drawing in `viewport-panel.tsx`, and the wiring (`marqueeCandidates`, `selectMany`) in `index.tsx`. Tests: `src/test/viewport-marquee.test.ts` (Node: maths, behind-camera and near-plane boxes, chunking, cache invalidation, selection rule, gesture on the controller) and `src/test-dom/viewport-marquee.test.tsx` (DOM: real pointer and key events for the drag, Shift/Ctrl/Cmd/Alt, Escape and the click slop).
- **Not verified.** The feel of the rectangle and its drawing in the live editor; whether Alt pressed and released alone during a drag moves the focus to the window's menu bar on Windows or Linux.

## Client statistics in the Engine panel

The Engine panel shows recent measurements from this client: editor frame request round trips, decoded RGBA pixel payload bytes/s (excluding protocol headers and unchanged-response metadata), frames actually drawn to the viewport canvas, event poll round trips and time since the last successful poll. A static editor view can show zero displayed frames/s because it only requests frames on changes. Game frame and clock progress use the existing GetPlayState frame/time counters per client wall second; they describe simulation progress, not host CPU or GPU frame time. Audio buffer milliseconds and underruns come from the current audio player's existing counters.

Measurements reset on connection changes, and stale in-flight responses cannot populate a reconnected session. Presentation rates reset when the viewport changes source. Missing or expired latency/progress samples show a dash; measured idle rates can be zero. The rolling window is at most five seconds, with at most 512 samples per metric and 128 play samples; if the cap shortens coverage, rates use the shorter measured interval. An injected monotonic clock makes the calculations deterministic. The panel refreshes at 4 Hz while connected and adds no engine requests. Poll timing is client-observed round trip and recency, since remote event timestamps cannot establish event age across unsynchronized clocks. Host timings, draw calls, memory counters and a Profiler tab remain EN5 work.

Tests cover bounded rolling rates, unavailable versus zero, monotonic timing, reconnect and source changes, counter resets, paused GetPlayState samples, existing PollEvents instrumentation, successful versus unchanged/stale/failed canvas presentation, and panel timer cleanup. The live Electron panel's visual layout has not been manually verified.

## Script editor (FE14)

Asset text tabs use locally bundled CodeMirror 6: Lua and JSON highlighting, line numbers, bracket matching, undo/redo, Tab indentation, Ctrl+F find/replace, and Ctrl+Space completion. Ctrl+S uses the existing configurable text-save action. AssetsState still owns the tab text, dirty state, original line endings, external-change warning/reload, and save failures. Play mode, viewer roles, and read-only hosts make the editor read-only through the existing canWrite guard.

Lua completion and hover use the annotation index in `src/renderer/lua/lua-api.generated.json`. Run `npm run sync-lua-api -- /path/to/N2Engine` after changing `engine-ref.txt`; it reads Git objects at that exact commit rather than whatever files happen to be checked out. CI regenerates both protocol and Lua data and rejects changes. Runtime scripts use `engine-api.lua`; paths under an `editor/` directory use the separate `editor-api.lua` index. At the current legacy pin the latter file does not exist, so its index explicitly records `available: false`; updating the engine pin will populate it. Tests cover the editor annotation shape independently.

Completion covers globals, dotted/colon class members (including inherited fields), a behaviour's `self.` methods and SerializableFields, and the field declaration keys. Hover shows documented types, signatures, parameters, returns and overloads as plain text. This small annotation parser does not infer arbitrary local-variable types or run project code.

The optional `ScriptEditor.checkSyntax(text, chunkName)` adapter and 500 ms latest-wins scheduler are ready for EN1. Only one check is in flight per editor, edits immediately clear stale diagnostics, and closing/switching a tab rejects late replies. Network failures are status text, distinct from compile errors. The protocol/IPC capability hookup waits for FE-S1 after EN1 merges; hosts without the adapter make no check requests.

CodeMirror fits the existing esbuild bundle and CSP without workers, eval, remote scripts or a language server. The exact dependency versions and MIT notices are in package-lock.json and THIRD_PARTY_NOTICES.txt. Measured with the unchanged Chrome 130, unminified, linked-source-map build: renderer.js grows from 849,088 to 2,199,490 bytes (+1,350,402); gzip level 9 grows from 199,316 to 452,999 bytes (+253,683). Source maps are excluded. The baseline was rebuilt from commit 718bf75 with its original assets-panel.tsx; the final build includes the generated runtime API data and editor/lint UI. Typing feel and appearance in the live Electron app still require a user check.

Validation includes the annotation parser fixtures, completion contexts, diagnostic location mapping and stale-reply scheduling; real CodeMirror DOM tests cover mounting, external reload, read-only changes, member completion, find/replace and Ctrl+S saving CRLF through the fake host. The existing two-tab keymap tests continue to verify that each file saves independently. jsdom supplies empty layout rectangles and animation frames, so these tests exercise editor behavior rather than visual layout.
